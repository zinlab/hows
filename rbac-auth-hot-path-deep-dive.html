Executive summary

haus-rbac-api is Haus's central authorization service. Every other service that needs to answer "can user X do action A in org O?" calls it over HTTP. The hot path is POST /permissions/check.

While load-testing during MCP-180, Cloud Trace showed the dominant request cost was not the databases — it was a single synchronous Firebase get_user network round-trip to Identity Toolkit, on every authenticated request:

Local JWT verify
~2 ms
Public-key fetch (cached)
~0.7 ms
Firebase get_user (network)
dominant span
~104 ms
DB query spans
none

Trace from POST /permissions/check on haus-development (image 953aabb). Dev numbers — JP flagged in-thread that prod will differ; the shape (one network hop dominating) is the point.

The decision that was reached

The team debated three options. Removing the call was rejected because it would force every consumer to become Firebase-aware (breaking the vendor-agnostic design). Shortening the token TTL is impossible (Firebase hard-codes 60 min). The chosen path — implemented on the zoeyhu/mcp-282 branch and documented in ADR-0014 — is a short-TTL, in-process, per-uid cache of the user record (default 30 s, 0 disables). The token is still fully verified on every request; only the get_user network call is cached. Revocation/disabled enforcement still runs every request and becomes at most TTL-stale.

The rest of this document explains every term in that summary from scratch, traces the code path end-to-end, reviews the broader architecture, and lists the issues and improvements that fall out of it.

No prior knowledge assumed

Foundations: authentication vs authorization

The entire debate hinges on a distinction that is easy to blur, so it's worth nailing down precisely.

Authentication (authn) — "who are you?"

Proving identity. For Haus this means a Firebase ID token (a JWT): a signed, time-limited credential issued by Firebase Authentication after a user logs in. Verifying it answers "is this a genuine, unexpired token for user U?"

Authorization (authz) — "what may you do?"

Given a known identity, deciding whether that identity holds a specific permission in a specific scope. This is RBAC's actual job: walking role → permission bindings to answer "does U have experiments:read in org acme?"

What a Firebase ID token (JWT) actually contains

A JWT is three base64 segments — header, payload (claims), signature. RBAC cares about these claims:

decoded ID token claims (conceptual)
{
  "iss": "https://securetoken.google.com/<project_id>",  // issuer
  "aud": "<project_id>",                                // audience
  "sub"/"uid": "abc123",                            // the user id
  "email": "zoey@hausanalytics.com",
  "auth_time": 1781700000,    // when the user actually logged in
  "iat": 1781707000, "exp": 1781710600, // issued-at / expiry (≤ 1h apart)
  "custom_claims": { "roles": [...], "role_admin": false }
}

The crucial insight that drove the ticket: uid, email, and custom claims are already inside the verified token. You do not need a network call to learn who the user is. The network call (get_user) exists only to fetch two pieces of server-side, live state that the token cannot carry:

  • disabled — whether an admin has disabled the account since the token was minted.
  • tokens_valid_after_timestamp — a server-side "revoke everything issued before this instant" marker, set on a "log out everywhere" / forced revocation.
Why "revocation is an authn concern" matters here

JP's framing in the thread: checking whether a token was revoked from another session is an authentication question (is this credential still valid?), not an authorization one (what may this user do?). RBAC took on that authn responsibility deliberately — so that consumers wouldn't have to. That deliberate choice is exactly what makes removing it expensive.

The conversation

The thread & MCP-282

The #mcp-eng thread (2026-06-17) opened with JP observing that the extra Firebase API call is responsible for ~60–70% of RBAC response time and is doing something that "feels like" an authn concern bolted onto an authz service. The discussion (JP, Christian, Martin, Zoey) converged through these beats:

  • Is it RBAC's job? Consensus: token-revocation checking is an authn concern. But RBAC took it on on purpose so consumers stay vendor-agnostic.
  • Who relies on it? Front-end consumers (ferry, internal tools) do their own authn; back-end consumers only do authz via RBAC. So if RBAC stops checking revocation, the BEs would have to start — pushing Firebase-awareness onto them.
  • Can we just shorten the token? No — Firebase hard-codes ID-token lifetime at 60 min; not configurable. ("Another reason to move away from Firebase.")
  • Latency anatomy: ~50–70 ms direct call (of which ~30–50 ms is the Firebase check) + ~100 ms added by the Cloudflare proxy DNS hop.
  • Landing point: Zoey leaned toward keeping the check and using a short-TTL cache — pushing Firebase-awareness onto consumers would break the vendor-agnostic design that is the point of RBAC. JP took the internal network gateway work (to remove the ~100 ms CF hop), which also helps canary-rollout traffic.

The three options, as framed in MCP-282

MCP-282 also flagged a documentation contradiction: API_SPEC.md said "Firebase 1-hour TTL is trusted; no active revocation is performed," while the code did perform per-request revocation. The work reconciles the spec to the code (active, TTL-bounded enforcement).

Systematic walkthrough

The auth hot path, step by step

Here is exactly what happens when a consumer calls POST /permissions/check, tracing through the real files. The two distinct "front doors" share the same identity-resolution core:

Entry styleUsed byHow the token arrives
POST /permissions/checkService-to-service authz (the six consumers)In the JSON body ({token, org, permission, adapter}). No Authorization header; the route is intentionally public.
require_permission(...) / require_authenticated_user() / require_staff()All other routes (/orgs/me, /roles, /access/* …)As a Authorization: Bearer <token> header via get_bearer_token().

The call chain

1
Token extraction & DB contextapi/dependencies.py → _resolve_auth() / route handler

The dependency sets the request-scoped DB context (pushes the pooled MySQL + Postgres handles into a ContextVar) and pulls the Bearer token. A finally: guarantees the thread's pooled connections are released on the same thread that checked them out.

2
Resolve user from tokenget_user_from_token() → User.find_by_token() → user_sources.get_source("firebase")

A typed TokenAuthResult captures the outcome class: missing | invalid_adapter | invalid_token | disabled | revoked. The User model holds no DB profile — identity comes entirely from the user-source adapter. The adapter is looked up in a registry (default "firebase").

3
Verify the JWT locallyFirebaseUserSource.find_by_token() → firebase_auth.verify_id_token() · span rbac.firebase.verify_id_token (~2ms)

Signature + expiry + issuer/audience are checked against Google's public keys (cached in-process). A second, explicit issuer/audience pin (ADR-0003 §1) rejects tokens from any other Firebase project — defense-in-depth against an Admin-SDK misconfiguration after the migration. No network hop here.

4
Resolve the user record — cache, then network on miss_user_cache.get(uid) → on miss: firebase_auth.get_user(uid) · span rbac.firebase.get_user (~104ms)

This is the step MCP-282 is about. The per-uid TtlCache is consulted first. On a hit, the ~100 ms Identity Toolkit round-trip is skipped entirely (the get_user span is simply absent from the trace). On a miss, get_user runs, the record is mapped to a dict, and the result is cached.

5
Enforce revocation & disabled — every requestauth_time vs tokens_valid_after · raises RevokedTokenError / DisabledAccountError

Crucially, enforcement runs on hits and misses. The fresh per-token auth_time is compared against the (possibly cached) tokens_valid_after_timestamp; the cached disabled flag is checked. A revoked or disabled account is rejected within at most the cache TTL.

6
Authorization: the actual permission checkservices/permission.py → check_permission()

Now RBAC does its real job. For an org-scoped check: (a) MySQL resolves the org and confirms it's active; (b) MySQL confirms the user is a member (user_organization); (c) Postgres walks role_binding → role → role_permission → permission. Global-only checks skip the MySQL org lookups.

7
Respond — with deliberate status semantics200 / 422 / 503

200 {"allowed": true|false} for every real decision (status-code parity kills the enumeration side-channel, ADR-0003 §2). 422 for a malformed permission string before any DB work. 503 {"detail":"<dep> unavailable"} when Firebase/MySQL/Postgres is unreachable, so callers can distinguish "denied" from "couldn't check" and retry (ADR-0007).

How it works under the hood

Low-level mechanisms

5.1 — The user-source adapter pattern

RBAC never imports Firebase directly into its routes. Instead it defines a UserSource Protocol (a structural interface) and resolves a concrete adapter from a registry. This is the seam that makes the service "auth-vendor agnostic."

haus_rbac/user_sources/base.py — the contract
class UserSource(Protocol):
    def find_by_token(self, token: str) -> dict | None: ...   # verify + return record, or None
    def find_by_ids(self, user_ids: list[str]) -> list[dict]: ...
    def find_by_email(self, email: str) -> dict | None: ...
    def find_by_email_domain(self, domain: str) -> list[dict]: ...
    def provision_user(self, record: dict) -> dict: ...

The registry (user_sources/__init__.py) registers Firebase only when FIREBASE_GCP_PROJECT is set, and get_source(name=None) defaults to "firebase". To swap providers you implement the Protocol in a new adapter and register it — no route or service code changes. That is the whole point, and it's why option B (pushing Firebase-awareness to consumers) was considered a regression rather than a refactor.

5.2 — Two Firebase operations, very different costs

OperationWhat it isNetwork?CostCacheable?
verify_id_token()Cryptographic verification of the JWT signature + claims against cached public keys.No (keys cached)~2 msRuns every request — no need.
get_user(uid)REST call to identitytoolkit.googleapis.com to fetch the live server-side user record.Yes — SDK does not cache it~104 msYes — the MCP-282 change.

The mapped record dict carries both fields enforcement needs (disabled, tokens_valid_after_timestamp), so caching that one dict serves the returned user and both enforcement checks from a single cached value.

5.3 — The revocation check, precisely

haus_rbac/user_sources/adapters/firebase.py — enforcement (runs on hit and miss)
# auth_time = when the user actually logged in (from THIS request's token)
# tokens_valid_after = server-side "everything before this is revoked" marker
auth_time = decoded.get("auth_time")
tokens_valid_after = record.get("tokens_valid_after_timestamp") or 0
if auth_time is None or auth_time * 1000 < tokens_valid_after:
    raise RevokedTokenError(uid)
if record.get("disabled"):
    raise DisabledAccountError(uid)

Two subtle, deliberate properties: a missing auth_time is treated as revoked (fail-closed), and because auth_time comes from the live token while tokens_valid_after may be cached, a "log out everywhere" that bumps tokens_valid_after is only invisible for as long as the stale cache entry lives — i.e. ≤ TTL.

5.4 — The TtlCache itself

The cache is intentionally tiny and boring (see user_sources/cache.py). Its properties are load-bearing for correctness:

In-process, per-pod

A Python dict guarded by a threading.Lock. Not Redis — a shared cache would re-introduce the very network hop we're removing. Each pod caches independently; the staleness bound holds on every pod.

Thread-safe

FastAPI runs sync routes on a thread pool, so every get/set/evict is under the lock.

Lazy expiry + size ceiling

Entries store a monotonic expires_at; an expired entry is dropped on read so a stale value is never served. A 10,000-entry ceiling evicts expired-first, then oldest-by-insertion, so a flood of distinct uids can't grow memory unbounded.

Kill-switch

FIREBASE_USER_CACHE_TTL_SECONDS=0 makes enabled false: get always misses and set is a no-op, restoring per-request enforcement instantly with no deploy.

5.5 — Supporting runtime machinery

  • ContextVar DB context. Pooled MySQL + Postgres handles live on app.state and are pushed into a ContextVar per request, so service/model calls don't pass connection objects around and can't accidentally hit the wrong DB.
  • Connection pooling (playhouse.pool). Warm connections are reused instead of reopened per request (a cold Cloud SQL connect was a prior latency driver). The sizing invariant: each pool's max_connections ≥ WEB_THREADPOOL_LIMIT, or a burst exhausts the pool (the 2026-06-12 incident).
  • Same-thread release. peewee's pooled state is thread-local, so connections must be released on the thread that checked them out — every auth dependency does this in a finally:.
  • OpenTelemetry spans. rbac.firebase.verify_id_token and rbac.firebase.get_user are manual spans; the absence of the get_user span in a trace is the signal that the cache served the request.
The implemented solution

The cache decision (ADR-0014)

ADR-0014 ("cache the Firebase user record on the auth hot path", Accepted 2026-06-17, driver Zoey Hu) records the decision. Its five "load-bearing properties" are worth internalizing because they're what make a cache on an auth path defensible:

  1. The token is fully re-validated on every request. Only the get_user network call is cached; the cache key is the uid, not the token. Signature/expiry/issuer-audience always run.
  2. Enforcement runs on every request, including hits. So a revoked/disabled account is rejected within ≤ TTL, always within the token's ≤1 h life.
  3. In-process, not Redis. Removing a network hop with a cache that adds a network hop would be self-defeating.
  4. Only successful lookups are cached. Firebase-unavailable exceptions still propagate for ADR-0007 503 handling and are never cached, so a transient outage retries next request rather than getting pinned.
  5. Disabled records are cached too — they keep denying without re-hitting Firebase; a re-enable becomes visible within the TTL. Symmetric with the revocation bound.
Net effect

Warm/bursty callers drop ~100 ms (down to local-verify + DB cost). The revoked/disabled enforcement window widens from ~0 to ≤ TTL per pod — at the default 30 s, far tighter than the ≤1 h window that fully removing the call (option B) would have imposed, and consumers stay Firebase-unaware. No new dependency, no schema change, no consumer change.

Status note: this lives on branch zoeyhu/mcp-282. The code, ADR-0014, and the reconciled API_SPEC.md wording are present there; security sign-off on the chosen TTL is an explicit acceptance criterion still open in the ticket.

Why it's built this way

Design considerations & tradeoffs

The vendor-agnostic boundary is the central design value

RBAC deliberately absorbed an authn responsibility (revocation/disabled enforcement) so that the ~6 back-end consumers can be pure authz callers that know nothing about Firebase. Every option in the thread was judged primarily against this boundary, not against raw latency. That's why a 100 ms win (option B) lost to a 100 ms win that preserves the boundary (option A).

The latency budget has two separable parts

RBAC direct (incl. Firebase)
50–70 ms
in-app
Cloudflare proxy DNS hop
~100 ms
network

ADR-0014 attacks the first part (the in-app Firebase span). The ~100 ms Cloudflare hop is a separate problem JP picked up: an internal network gateway so internal callers bypass the public rbac.haus.io CF path. These are complementary — the cache helps every caller; the gateway helps internal callers and also the canary-rollout traffic (related: MCP-283, parameterize web workers + per-env resources for bursts).

Choosing the TTL is a security-posture dial

TTLHot-path savingsMax revoke/disabled stalenessWhen appropriate
0None (every request hits Firebase)~0Kill-switch / rollback; incident requiring instant revocation.
30 s (default)High for bursty callers≤ 30 s/podNormal operation — the chosen balance.
60 s+Higher≤ 60 s+/podIf traffic is very bursty and security review accepts the wider window.

Why the /permissions/check endpoint is public — and how that's contained

An intentional ADR-0003 decision: the endpoint must be reachable by any consumer from anywhere, and adding caller authentication across six in-flight consumers was judged too expensive to gate on. The endpoint stays public, hardened with in-process defense-in-depth:

  • Issuer/audience pin — rejects tokens from any other Firebase project (catches Admin-SDK misconfig post-migration).
  • Status-code parity on deny — every deny returns 200 {"allowed": false}, so a probe can't distinguish "bad token" from "valid token, no permission" (no enumeration oracle, no token-liveness oracle).
  • Per-subject rate limit — 60 checks/min/uid via a Redis permcheck:* counter; over-limit returns a normal deny. Redis down → fail-open (no request blocked).
  • 422 on malformed permission — a regex gate (^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$, ≤128 chars) rejects junk before any DB work.
  • 4 MB body cap + per-call audit log — bound memory on an unauthenticated endpoint and make abuse visible.

The deliberate two-database split

User/org ground truth stays in the legacy MySQL (Harbor-owned, read-only here) where the rest of the platform already reads/writes it; RBAC-owned state (roles, permissions, bindings, the Access Center tables) lives in a dedicated Postgres versioned with dbmate. This avoided a large data migration and kept the rollout blast radius narrow — at the cost of coupling to a database RBAC doesn't own (see issues below).

Context from downstream

Downstream consumers: how RBAC is actually called

The two MCP services confirm the contract and illustrate why the vendor-agnostic boundary matters. Both forward a user Firebase ID token to RBAC; neither implements RBAC's authz logic itself.

haus-mcp-internal — the explicit client

src/haus_mcp/rbac.py is a direct, readable client. It documents the contract verbatim and treats 400/401/403 as denial:

haus-mcp-internal/src/haus_mcp/rbac.py — the call
response = await rbac_client.post(
    "/permissions/check",
    json={"token": firebase_token, "org": org_name_as_key,
          "permission": permission, "adapter": "firebase"},
    timeout=timeout)
response.raise_for_status()
# 400/401/403 → PermissionDenied; data["allowed"] gates the tool

Two hardening details worth noting (both from prior security scans):

  • Fail-secure when misconfigured. If the RBAC client is None in a non-development environment, the call is denied — a prior bug let an empty rbac_service_url silently authorize every employee.
  • Anti-retry denial wording. The denial message explicitly tells the LLM not to retry — a confused agent previously cycled tools against a forbidden org, treating denial as transient (ENA-109).

haus-mcp — the same contract behind a Port

haus-mcp uses a hexagonal architecture: tools depend on an RbacPort Protocol; the HTTP RbacClient is the only adapter, and an in-memory fake satisfies the same Protocol in tests. It also reveals the other layer of the token story.

A second token cache lives in the consumer

Because MCP clients (LLMs) authenticate via stored OAuth refresh tokens rather than a live browser session, haus-mcp mints a fresh Firebase ID token per downstream call via FirebaseIdTokenForwarder, and caches that ID token in Redis for 50 min (kept under Firebase's 60 min lifetime). On /oauth/revoke it calls invalidate() to drop the cached token so a revoked session can't keep using it for up to 50 min.

The layered staleness picture

Putting it together, a "true logout" has to propagate through up to three independent windows, which is the real-world version of Martin's "the calling service may not know until too late" concern:

LayerMechanismStaleness window
Firebase ID tokenHard-coded token lifetime≤ 60 min (not configurable)
haus-mcp forwarderRedis ID-token cache + invalidate() on revoke≤ 50 min (0 if revoke calls invalidate)
RBAC user-record cacheIn-process TtlCache (ADR-0014)≤ 30 s per pod

RBAC's new cache adds the smallest window of the three by a wide margin — which is part of why option A was defensible.

Assessment

Architecture review

What's strong

Clean authn/authz seam

The UserSource Protocol + registry genuinely isolates the vendor. Swapping Firebase is an adapter change, not a surgery.

Decisions are written down

14 ADRs, per-module CLAUDE.mds, an architecture doc, runbooks, and a pentest suite. The "why" survives turnover — rare and valuable.

Thoughtful failure semantics

Deny / couldn't-check / malformed are three distinct response classes; fail-open vs fail-closed choices are explicit (rate-limit open, missing auth_time closed).

Security-first hot path

Issuer/audience pin, enumeration-oracle collapse, body cap, audit logging, and a real pentest harness on the public endpoint.

Potential issues — high level

  • Per-pod cache inconsistency. Each pod's cache is independent, so the effective revocation window is "≤ TTL on the pod that happens to serve the request." With N pods and load-balancing, a revoked user may be denied by one pod and (briefly) allowed by another until all entries expire. Acceptable at 30 s, but it should be stated as the actual guarantee, not "≤ TTL globally."
  • Synchronous HTTP authz is a shared hot path. Central authorization over HTTP is a single source of truth and a single chokepoint; the architecture doc itself flags "revisit if the web pod becomes a bottleneck." The Firebase call was the first ceiling; the next is connection/thread capacity under canary bursts (hence MCP-283).
  • Coupling to a database RBAC doesn't own. The Harbor MySQL dependency brings manual GRANTs that fail only at runtime and can't be enforced in CI — a recurring foot-gun and an availability dependency on another team's instance.
  • No active revocation signal. Revocation is entirely pull-based (poll Firebase). There's no push/webhook path, so the floor on staleness is fundamentally Firebase's, and "instant logout" isn't achievable without either polling every request (TTL=0) or a new mechanism.
  • The ~100 ms Cloudflare hop dominates once Firebase is cached. After ADR-0014, the CF proxy DNS hop becomes the largest remaining cost for internal callers — addressed only by the separate gateway workstream.

Potential issues — low level

  • No negative/short-error caching. Only successful lookups are cached (correctly, re: outages), but a uid that legitimately 404s in Firebase, or a hot invalid token, still pays the network cost every request — a possible amplification vector on the public endpoint.
  • No cache observability surfaced yet. There's a per-span user_cache_hit attribute, but no hit-rate metric/counter called out alongside the existing rbac_* metrics. Tuning the TTL and proving the win in prod needs a hit-ratio gauge.
  • No request coalescing (single-flight). On a cold cache, a burst of concurrent requests for the same uid each fire their own get_user; under the canary-burst scenario this is exactly when the network cost multiplies.
  • No TTL jitter. Entries written together (e.g. a burst after a deploy) expire together, producing a synchronized refresh stampede every TTL.
  • Rate limit keyed only on subject uid. Pre-auth junk (bad tokens) isn't rate-limited by subject because there is no subject; the 4 MB cap and 422 gate help, but unauthenticated volume on a public endpoint is only partially bounded.

If I were picking up MCP-282 from here

The cache is implemented and well-reasoned. The remaining high-value work is (1) ship the hit-ratio metric and capture prod before/after traces to satisfy the acceptance criteria, (2) get the security sign-off on the 30 s TTL with the per-pod window stated honestly, and (3) keep the CF-gateway track separate so it isn't blocked on the cache. Glossary

JWT / ID tokenSigned, time-limited credential carrying user claims (uid, email, custom claims, auth_time, exp).
verify_id_tokenLocal cryptographic check of a JWT against cached public keys (~2 ms, no network).
get_userNetwork call to Firebase Identity Toolkit for live server-side user state (~104 ms; the cached call).
tokens_valid_afterServer-side marker; tokens with an earlier auth_time are treated as revoked.
role_bindingPostgres row binding a user to a role in a scope (global or per-org); the unit RBAC walks to permissions.
name_as_keyAn org's short-name key used in /permissions/check (distinct from the subdomain slug ferry routes by).
