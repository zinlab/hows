      ◆ The surface
      Chapter 01

      The surface at a glance

      Before judging anything, map it. haus-mcp-internal exposes 69 tools spanning ten loosely-bounded families. The shape of that surface — what's big, what's duplicated, what depends on what — already predicts where a model will struggle.

      This review was written against the live tool definitions, not a spec document — every schema, parameter, enum, and description quoted here was pulled directly from the running server. The families below are the author's grouping; the codebase itself encodes them only as name prefixes (get_cmmm_*, get_facebook_*, list_*).

      The one parameter every tool shares

      All 69 tools require org_name_as_key. There is no set_organization, no session-scoped default — every call, in every chain, re-states the organization. Hold that thought; it's the subject of Chapter 6.

      What this review optimises for

      One yardstick, applied throughout: can a non-deterministic reader (a) find the right tool among 69, (b) populate its schema correctly on the first try, (c) get back signal it can use, and (d) feed that output into the next tool in the chain? Every issue below is a place where one of those four breaks, and every fix is followed by the mechanical reason it helps — because "be consistent" is advice, but "a shared parameter name lets induction heads copy the value from the previous tool's output instead of re-deriving it" is an explanation you can design against.

      ★ The headline

      This is a capable, actively-maintained server with real sophistication — graceful payload truncation, posterior-probability guidance, per-tool permission scopes. Its weaknesses are not crude; they are the subtle, compounding kind: identity concepts that drift in name and type across families, constraints written in prose the schema doesn't enforce, and a tool count that dilutes selection. None is fatal alone. Together they tax every multi-step task.

      ✓ Strengths
      Chapter 02

      What the server already gets right

      Credit before critique — and these aren't throwaway compliments. Several patterns here are more advanced than most production MCP servers ever reach, and the fixes in later chapters are mostly about propagating these good patterns to the families that lack them.

      1 · The paid-media families are internally coherent

      Every Facebook and Google getter speaks the same dialect: date_from / date_to for the window, campaign_name for a partial-match filter, limit / offset for pagination, and a group_by enum for aggregation. A model that learns one of these tools has effectively learned all twenty-one. This is exactly the transfer you want — and it's the proof that the team can do consistency; it just hasn't been enforced across family boundaries (Chapter 3).

      paid_media_shared_shape.txtconsistent within family
      // The same 5 parameters, tool after tool:
date_from   // "YYYY-MM-DD"
date_to     // "YYYY-MM-DD"
campaign_name?   // partial match
limit?      // default 100, max 1000  (documented!)
offset?     // default 0
group_by?   enum["daily","daily_campaign","ad"]  // real schema enum

      2 · Token economy is taken seriously

      This is rare and worth applauding. Several cMMM tools accept chart_data_granularity: "weekly" | "summary_only" to let the caller drop heavy per-channel arrays — and, crucially, the server auto-falls-back to summary_only when a projected payload would exceed the harness limit, appending forced_summary_only_due_to_payload_size to a warnings array. Add compact (drop all-zero rows), top_k (return only the N largest), and which_read (fetch one readout instead of three), and you have a server that actively manages the model's context budget. Most servers return everything and hope.

      ⟐ Why this matters mechanically

      A tool result is appended verbatim to the context and then attended over on every subsequent step. An unbounded 4,000-row dump doesn't just cost tokens once; it dilutes every future attention distribution and pushes the conversation toward the context ceiling. By truncating at the server — and signalling that it did via a warning the model can act on — the design keeps the signal-to-token ratio high without the model having to know in advance how big a response will be.

      3 · Descriptions teach interpretation, not just mechanics

      The experiment tools embed genuine analytical guidance: read reporting_category and kpi_name together before making any unit-bearing claim; lead with prob_lift_gt_zero rather than collapsing to "the CI crosses zero, therefore inconclusive"; consult cross_cell_note when cell-vs-cell entries appear. This is behavioural steering that measurably improves how the model reasons about the data after it arrives — not merely how it calls the tool. (Chapter 8 argues this content is correct but lives in the wrong place.)

      4 · Least-privilege scopes and discovery bootstrapping

      Two more mature choices. First, tools carry explicit permission scopes (mcp_internal_cmmm_past_performance:read) rather than one blanket grant — the blast radius of any single tool is bounded. Second, the surface is honest about its opaque IDs: it ships list_* tools (list_cmmm_contexts, list_design_playground_configs, list_regions) whose entire job is to hand the model the valid IDs it can't know a priori. That is the correct pattern for a server fronting real datasets — the problem (Chapter 3) is only that the IDs they hand back are named inconsistently by the tools that consume them.

      5 · Resilience is designed in

      When a Fivetran table may be unsynced, the ad-level tools document a concrete fallback ("if this returns table-not-found, use get_facebook_adset_performance instead"). The intent — graceful degradation rather than a dead end — is exactly right. Chapter 7 argues only that this recovery belongs inside the server, not in a description the model has to remember to act on.

      ★ The through-line

      The raw materials of an excellent MCP server are already here: a proven consistent dialect (paid media), real payload discipline, interpretive guidance, scoped permissions, discovery tools. Almost everything that follows is about extending these wins to the families that missed them and moving guarantees from prose into the schema and the server, where they bind deterministically instead of probabilistically.

      ▲ Schema · Identity
      Chapter 03

      The inconsistency tax

      This is the most consequential finding in the review. Across the surface, the same underlying concept — a KPI, a readout, a date window, a region — travels under different parameter names, and sometimes different types, depending on which family wrote the tool. The server already documents that this causes hard call failures.

      Each family is internally consistent (Chapter 2). The damage happens at the seams between families, where a model that just succeeded with one tool carries its learned vocabulary into the next and gets rejected. Here is the drift, concept by concept:

      This isn't hypothetical. The cMMM tool's own description carries a warning that only makes sense if models get this wrong constantly:

      from get_cmmm_past_performance descriptiondocumented footgun

      The model is being warned not to do the thing that every other KPI-aware tool trained it to do — pass a name_as_key. The inconsistency manufactured the footgun; the warning is a patch over it.

      ★ Why it costs you — the mechanism

      A transformer doesn't "look up" your API; it predicts the next token by analogy to patterns it has seen, including patterns earlier in this very conversation. Two mechanisms are at work:

      (1) In-context learning. When the model sees kpi_name_as_key: "new_orders" succeed on tool A, it forms a transient association — this concept is addressed by a human-readable key — and pretraining reinforces that fields literally named *_name or *_key take strings. That prior transfers to tool B. If B agrees (kpi_key), the transfer is a free win. If B instead wants a numeric kpi_id, the prior actively mis-fires: the model confidently passes the wrong-typed value and the server rejects it.

      (2) Induction heads. The mechanism that lets a model chain tools is literally copy-by-pattern: an induction head sees list_cmmm_contexts return {"164": ...} and, at the next call site, copies 164 into the slot that looks like where it goes. A single shared name (kpi_id in both the discovery output and the consumer input) makes that copy reliable. Five different names for one concept break the visual/positional cue the induction head relies on, so the chain snaps in the model's head — exactly where multi-step analytics tasks live.

      Every additional name for one concept multiplies the hypotheses the model must disambiguate at call time, under load, and defeats the very circuit that would otherwise carry an ID from one tool's output into the next tool's input.

      The fix: one canonical vocabulary, enforced

      Pick one name and one type per concept, server-wide, and make every tool speak it. The drift collapses into a single learnable mapping:

      How to ship it without breaking in-flight agents

      You can't rename a parameter out from under a running conversation, so do it additively. Accept the new canonical name and the legacy name simultaneously, normalise to canonical inside the handler, and mark the legacy alias deprecated in the description. Remove the alias only once usage telemetry shows it has drained.

      alias_and_normalize.pyadditive migration
      def resolve_kpi(args):
    # accept canonical OR any legacy alias, coerce to str
    raw = (args.get("kpi_id")
           or args.get("kpi_key")
           or args.get("kpi_name_as_key"))
    if raw is None:
        raise ToolError("kpi_id is required; "
            "call list_cmmm_contexts to get valid ids")
    return str(raw)   # one type at the boundary
      ⟐ Why the alias works mechanically

      The model's mis-fire (Chapter mechanism above) is that it passes kpi_key or a name when the schema wanted kpi_id. An alias makes the model's most probable wrong guess correct — you meet the prior instead of fighting it — while normalisation guarantees the handler sees one type. Over the deprecation window you then retrain the in-context prior toward the canonical name by making it the one the schema advertises and the descriptions use, so new conversations converge on it without any hard failures along the way.

      ▲ Schema · Constraints
      Chapter 04

      Enums that aren't enums

      The server already knows how to express a closed value set in the schema — group_by, breakdown, and fallback_method are proper JSON Schema enums. But a long list of equally-closed parameters are declared as bare string (or integer) with the legal values buried in the prose. The model is left to guess, unmasked.

      A representative sample of values that are closed sets in reality but free types in the schema:

      ParameterDeclared asActually constrained to (per prose)

      accounting_modestringcash · accrual

      ★ Why the enum wins — the mechanism

      Two distinct effects, both real:

      (1) Constrained decoding. Most modern tool-calling stacks generate arguments under grammar-constrained or schema-constrained sampling. When a field declares enum: [...], the decoder builds a token mask so that at that position only tokens consistent with a legal value can be sampled. An invalid value isn't "unlikely" — it is literally unreachable. The error rate for that field collapses to ~0 regardless of how the model "felt" about casing or synonyms. A bare string imposes no mask: the model free-samples and any drift survives.

      (2) Conditioning strength. Even where a harness doesn't hard-constrain, an enum is a far stronger signal than prose. The model was trained to fill schemas; the enum array sits in the slot it's filling, adjacent to the type, in the exact structure its tool-use training distribution rewards. A constraint written in a sentence three lines into a docstring must instead be (a) attended to and (b) correctly reproduced — two extra failure points. The enum moves the legal set from "something to recall" to "the shape of the hole."

      The numeric case is the same story: lookback_window as a free integer invites 30 or 90 (sensible-looking, backend-invalid); enum:[1,7,14,28] makes those unsamplable.

      Belt and suspenders: normalise at the boundary too

      Constrained decoding isn't universal across every client, so pair the enum with cheap server-side normalisation — lower-case, strip punctuation, map known synonyms — before validation. The enum stops most errors structurally; the normaliser catches the rest and turns a hard reject into a silent success.

      normalize_enum.pyforgive near-misses
      _ALIASES = {"lastclick":"last_click", "last-click":"last_click"}
def norm_model(v: str) -> str:
    k = v.strip().lower().replace(" ","_")
    k = _ALIASES.get(k, k)
    if k not in {"last_click","first_click","linear"}:
        raise ToolError(f"attribution_model must be one of "
            f"last_click/first_click/linear, got {v!r}")
    return k

      Note the error message also teaches the legal set — which is the subject of Chapter 7. An enum that rejects silently with "validation error" wastes the round-trip; one that names the alternatives lets the model self-correct in a single retry.

      ⚠ The consistency-of-consistency trap

      The danger here isn't that enums are unknown to the codebase — it's that they're applied to some fields and not others, with no obvious rule. A model (and a human contributor) can't form a reliable expectation when group_by is enforced but attribution_model isn't. Adopt a flat rule — every closed value set is a schema enum, no exceptions — so the pattern itself becomes learnable.

      ✦ Scaling
      Chapter 05

      Sixty-nine tools, competing for attention

      A 69-tool surface pays two taxes: every definition sits in context on every turn, and — more insidiously — dozens of near-identical getters blur together at selection time. Twenty-one paid-media tools that differ mostly by table or granularity are twenty-one descriptions the model must tell apart.

      For calibration against published figures: Anthropic has reported that on the order of 58 connected tools consume roughly 55K tokens of definitions, a single large connector ~17K, and one internal agent carried 134K tokens of tool definitions before optimisation. A 69-tool server with the verbose, methodology-laden descriptions seen here is squarely in that territory.

      Tax one: definitions in the prefix

      Tool definitions live in the context prefix and are attended over on every step. Self-attention is roughly quadratic in sequence length, so a large, always-resident tool block inflates latency and consumes the budget the actual task needs. It also pins the KV cache: a definition block that changes shape forces recomputation.

      Tax two: the selection-margin collapse

      This is the subtler and more damaging one for this server. Picking a tool is a classification over the candidate set. The model scores each tool against the request; the right one wins if its score sits clearly above its neighbours. But get_facebook_ad_performance, get_facebook_adset_performance, get_facebook_adset_country_performance, get_facebook_adset_summary… have highly similar names and descriptions — their embeddings are near-collinear. The logit margin between "the right one" and "a plausible sibling" is thin, so selection errors rise precisely where the surface is densest.

      Lever 1 — consolidate the granularity variants (design, not platform)

      Start here, because it shrinks the surface permanently. The tell is already in the schema: get_facebook_adset_performance accepts group_by ∈ {daily, daily_adset, adset, campaign} — it already rolls up to campaign level. So a separate campaign-only tool, or an ad-level tool that's "the same but one level down," is often a group_by/level value in disguise. Where the underlying tables permit, fold siblings into one tool with a level enum and let the server pick the table. Each fold removes a definition and widens the margin between the survivors.

      ★ Why consolidation helps twice — the mechanism

      Merging near-duplicate getters does two mechanically distinct things. (a) Fewer tokens: one definition instead of four cuts the resident prefix directly. (b) Wider selection margin: the model is no longer asked to discriminate between four tools whose descriptions are 90% cosine-similar — that ambiguous four-way softmax is replaced by one unambiguous tool plus an intra-tool enum choice (level), which is a constrained-decoding decision (Chapter 4), not a fuzzy semantic one. You convert a hard classification problem into an easy masked-sampling problem.

      Lever 2 — defer the long tail with a Tool Search Tool

      After consolidating, you still have a genuinely large surface. Keep the handful of highest-frequency tools eagerly loaded and mark the rest defer_loading: true behind a search tool, so their full schemas are fetched only when selected. The definitions stop living rent-free in the prefix, and — counter-intuitively — selection accuracy tends to improve, because the model searches a curated shortlist instead of scanning 69 competing descriptions.

      Lever 3 — push fan-out into code (Programmatic Tool Calling)

      Many real Haus questions fan out: "compare this experiment's lift across every org it ran in," "sweep budget×holdout for power." Done conversationally, every intermediate payload lands in context. With allowed_callers: ["code_execution_20250825"], the model writes sandbox code that calls the tools, joins and filters there, and returns only the distilled answer — the 4,000-row intermediate never enters the conversation.

      Lever 4 — serve discovery data as Resources, not tool calls

      Twelve list_* tools exist mainly to hand back IDs. Every ID lookup is a full tool round-trip plus its result in context. Much of this is reference data (the org's KPI list, region list, cMMM contexts) that fits MCP's Resources primitive — addressable by URI, fetched by the host without spending a tool call, and re-usable across turns. The model references kpi://org/contexts instead of paying a call to rediscover it each time.

      Decision tree

      Which lever for this server's bottleneck?

      What's the symptom you're actually seeing?

      Near-duplicate descriptions are what's confusing the classifier. Merging them widens the logit margin and turns the choice into a masked enum decision. Do this first — it's permanent.

      ⟐ Order matters

      Consolidate first (it shrinks and disambiguates), then defer (it hides what remains), then reach for programmatic calling and resources for the workload-specific wins. Deferring before consolidating just hides duplicates you should have deleted.

      ■ Semantics · State
      Chapter 06

      The org you repeat 69 ways, and the customer that usually-but-not-always equals it

      Two state problems compound here. Every tool re-demands org_name_as_key — there is no session default. And several tools also take a separate customer key that is, per the server's own words, "often but not always equal to org_name_as_key." That "usually equal" is exactly the shape of trap a non-deterministic reader falls into.

      Problem A — org as mandatory per-call boilerplate

      Because org_name_as_key is required on all 69 tools and nothing carries it as state, a five-step analytics task restates the organization five times. Each restatement is independent: a fresh opportunity to omit it, or — worse — to drift to a different org midway when the conversation has discussed several.

      ★ Why repetition erodes reliability — the mechanism

      Treat each required, model-supplied argument as an independent Bernoulli trial with some small per-call error probability p. Across a chain of n calls, the probability that every org argument is correct is (1−p)n — it decays multiplicatively. At p=2% and n=6 you've already shed ~11% of whole-task success to this one field. Removing an always-required argument from the model's job doesn't shave a little latency; it removes a whole multiplicative factor from the failure expansion. Fewer degrees of freedom per call is the single most reliable way to raise end-to-end success on long chains.

      MCP has no first-class mutable session-state primitive, so there's no perfectly clean fix — but two pragmatic options both reduce the burden:

      • A session-default tool. Add set_active_org(org_name_as_key) that caches the value server-side keyed by the connection/session, and make org_name_as_key on every other tool optional, defaulting to the active org. The model states it once; subsequent calls inherit it. (Document clearly that it's sticky, to avoid the model assuming it reset.)
      • Carry it in discovery. If you adopt Resources for reference data (Chapter 5), the org is implicit in the resource URI the host already holds, so data tools can resolve a default from context rather than re-prompting the model.
      session_default_org.pystate it once
      # org becomes optional everywhere; resolved from session
def resolve_org(args, session):
    org = args.get("org_name_as_key") or session.active_org
    if not org:
        raise ToolError("no org set — call "
            "set_active_org first, or pass org_name_as_key")
    return org

      Problem B — two identity keys that usually coincide

      Attribution and cMMM-campaign tools take both org_name_as_key and customer ("Customer dataset key... often but not always equal to org_name_as_key"). This is the most dangerous kind of parameter pair: two slots whose values are usually identical but occasionally must differ.

      ★ Why "usually equal" is a trap — the mechanism

      In-context learning generalises from what it sees. If, across most examples and most of this conversation, customer == org_name_as_key, the model learns the rule "these are the same thing" and starts treating customer as a redundant echo of org — it will happily set them equal by default. That heuristic is right most of the time and silently wrong exactly when it matters (the org whose dataset key differs), and because the call still succeeds-looking, the error is a wrong-data error, not a loud rejection. The high base-rate of equality actively trains the model into the failure.

      Two ways out, best first:

      • Make it derivable. If the customer dataset key is a deterministic function of the org for all but a handful of cases, resolve it server-side from org_name_as_key and expose customer only as an explicit override for the exceptions. The model supplies one identity; the server knows the mapping. The trap disappears because the model is never asked to reconcile two near-identical values.
      • If it must stay, maximise semantic distance. Rename customer → customer_dataset_key and have its description lead with how it differs from org, with a concrete unequal example. A longer, more distinct name and a difference-first description push the two fields' token representations apart, lowering the chance the model collapses them — and a default-from-org keeps the common case correct.
      ⚠ Don't fix repetition by making org optional without a default source

      Simply dropping org_name_as_key from "required" with nowhere to resolve it from trades a verbose-but-correct surface for a silent-wrong-default one. The fix is to relocate the value to state the server can resolve (session or resource), not to make a load-bearing argument quietly optional.

      ⬢ Errors & guards
      Chapter 07

      Errors, fallbacks, and resource guards

      The server already thinks about failure — it documents fallback paths and warns about expensive queries. The refinement: move that handling out of the prose, where it depends on the model reading and obeying it, and into the server, where it binds deterministically.

      Recovery written in prose is recovery the model has to remember

      Two Facebook tools carry the same instruction: "if this returns a table-not-found error, use get_facebook_adset_performance instead." The intent is good. But consider the path that recovery actually takes today: the model must (1) have read that sentence, (2) recognise the specific error as the documented one, (3) decide to issue a second call to a different tool, and (4) spend another round-trip and more context doing it. Every one of those steps is a probability less than one.

      recovery_in_prose.txtprobabilistic + 2 round-trips
      call get_facebook_ad_performance
  → "table not found: basic_ad"
model must: recall the note, recognise
  the error, choose the other tool,
  re-issue the call …
  (each step can fail)
      recovery_in_server.txtdeterministic + 1 hop
      call get_facebook_ad_performance(level="ad")
  server: basic_ad unsynced →
  transparently query basic_ad_set,
  return data + warning:
  "served_at_adset_level: basic_ad
   not synced for this org"
      ★ Why server-side fallback wins — the mechanism

      Prose fallback makes recovery a second inference problem: it consumes another generation, another tool round-trip, and more resident context, and it only fires if the model both attended to the note and classified the error correctly. A server-side fallback makes recovery a deterministic branch — zero model tokens, zero extra round-trip, fires 100% of the time the condition holds. You move the recovery from "probabilistic and expensive" to "certain and free," and you hand the model a structured warning so its narration to the user stays accurate.

      Case study: when a backend error leaks raw

      search_experiments_tool has been observed to fail on at least one org with a backend SQL type-casting error rather than a clean result. Whatever the root cause, the interface lesson is general: an opaque database exception is the worst possible thing to hand a model. It carries no actionable structure, so the model can neither retry intelligently nor explain the failure — it typically loops or apologises.

      leaked.jsonnothing to act on
      { "error": "could not cast type "
  "character varying to integer at "
  "experiments.cell_count …" }
// model: ¯\_(ツ)_/¯ → retry identically
      handled.jsonstructured + actionable
      { "isError": true,
  "code": "upstream_unavailable",
  "message": "experiment search is "
    "temporarily unavailable for this "
    "org; try get_experiment by id, or "
    "retry without include_archived",
  "retryable": false }

      Catch backend exceptions at the tool boundary, map them to a small set of stable error codes, and return them as isError: true tool results (not protocol-level faults) with a message that names a concrete next move. The model can then route around the failure instead of battering it. (And fix the cast — but the boundary handling is what protects every future backend hiccup, too.)

      Resource guards: a warning the model can ignore vs a limit it cannot exceed

      Several first-party-KPI tools warn: "keep date ranges to 30 days or fewer; each additional day scans ~150–230 MB in BigQuery; ranges over 30 days will be rejected." That guard protects a metered, expensive backend — but it lives in prose and a runtime rejection. A model that doesn't attend to the note asks for 365 days, triggers a costly scan or a hard reject, and burns a round-trip.

      ★ Why a structural guard beats a prose guard — the mechanism

      A prose limit is honoured only if the model reads and respects it — probabilistic, and the failure mode is a cost event on a per-byte-billed warehouse, which is a denial-of-wallet vector as much as a UX one. Two structural alternatives remove the gamble: (a) server-side clamp — silently cap the window to 30 days (or the max safe span) and return a window_clamped warning, so an over-broad request becomes a safe one automatically; or (b) server-side chunking — accept the long range, page it into ≤30-day scans internally, and stitch the result. Either converts "the model must know better" into "the server cannot be made to overspend." The constraint is enforced by control flow, not by the reader's diligence.

      ⟐ Keep the two error layers distinct

      Reserve protocol/JSON-RPC errors for malformed or transport-level problems. For business failures the model should react to — no data, upstream down, bad filter combination — return a normal tool result with isError: true and an actionable message. Mixing the two (raising a transport error for "no rows") denies the model the chance to recover in-band.

      ■ Semantics · Docs
      Chapter 08

      Descriptions that do too much — and the examples that are missing

      The experiment descriptions are encyclopaedic: unit-grounding rules, how to read prob_lift_gt_zero, daily-vs-published nuances, even Jira ticket numbers. The guidance is correct and valuable — but it's always resident and mixes two jobs. Meanwhile the one tool that most needs a worked example, the power-analysis grid search, has none.

      One description, two jobs

      get_experiment_results is doing both of these at once:

      • The contract — what it does, its parameters, the shape it returns. The model needs this at selection time, on every turn, to decide whether to call it.
      • The methodology — "lead with prob_lift_gt_zero; don't collapse to CI-crosses-zero; read reporting_category with kpi_name before any unit claim; for no-holdout 3-cell tests expect cell-vs-cell entries…" The model needs this only after results arrive, when it's interpreting them.
      ★ Why the split matters — the mechanism

      Everything in a tool description is paid on every turn the tool is even a candidate, because the whole tool block is resident in the prefix and attended over during selection. The methodology paragraphs therefore impose two costs on turns where no experiment is being interpreted: (a) raw token weight in the always-on prefix, and (b) selection-time dilution — long descriptions make the inter-tool comparison noisier (more text to differentiate, Chapter 5). Yet the methodology is genuinely useful when results are in hand. The resolution is to put each piece where it's cheap: a tight contract in the tool description, and the interpretive guidance in a place the host injects only when relevant.

      Move methodology into a Prompt or Resource

      MCP gives you two homes for the interpretive guidance, both better than the always-on description:

      • An MCP Prompt — e.g. interpret_experiment_results — that packages the "how to read lift" framing as a reusable template the user (or host) invokes when they're actually analysing a readout. The steering arrives exactly when it's load-bearing and costs nothing the rest of the time.
      • An MCP Resource — a short "reading experiment results" doc addressable by URI — that the host attaches to the context only on interpretation turns.

      ⟐ And drop the ticket numbers

      (per ENA-123) conditions nothing useful in the model and costs tokens on every load. Internal provenance belongs in the code comment or commit, not the tool description the model reads. Same for table-join trivia ("joins creative_history → ad_history → …") unless it changes how the model calls the tool.

      The missing examples: design_playground_power_analysis

      This tool has ~16 parameters, a nested-object schema (cell_b_ranges: {budget_range:{min,max,step}, cpi_range:{min,max,step}}), and a conditional requirement (cell_c_ranges is required only when cardinality="three"). Types alone do not tell the model how deep to nest or when the conditional fires — and this is precisely the profile of tool on which models produce malformed calls. It ships with no examples.

      ★ Why an example beats a longer docstring — the mechanism

      A nested, conditional schema is under-determined by its type signature — there are many syntactically-valid-but-wrong nestings. A worked example supplies a concrete template the model copies and mutates rather than synthesises from scratch: the same induction-head machinery from Chapter 3 lets it lift the {budget_range, cpi_range} structure verbatim and substitute values, which is far more reliable than reconstructing two levels of nesting from prose. The second example demonstrates the conditional (cardinality="three" ⇒ cell_c_ranges present), resolving by example what a sentence ("required when…") leaves the model to infer. Published results put complex-schema call accuracy rising from roughly 72% to 90% with a handful of such examples — concentrate them on exactly the nesting and conditionals, not the obvious scalar fields.

      Sequencing

      Phase 1 — same-day, pure upside. Add enums to every closed value set, wrap backend calls in an error boundary that returns actionable isError results, clamp the BigQuery window server-side, and strip ticket numbers and join-trivia from descriptions. None of these changes a call signature; all of them raise first-try success or cut tokens immediately.

      Phase 2 — additive, deprecation-gated. Introduce the canonical vocabulary (Ch.3) as aliases the handlers accept alongside the legacy names, normalising to one type at the boundary; default customer from org; add transparent table fallback; move the experiment-interpretation guidance into a Prompt. Each is backward-compatible, so in-flight conversations keep working while new ones converge on the better surface.

      Phase 3 — structural. Consolidate the paid-media getters behind a level enum, stand up the Tool Search Tool with the long tail deferred, add set_active_org and make org_name_as_key optional, and migrate the heaviest discovery lists to Resources. These reshape the surface and deserve their own eval pass (next paragraph).

      ★ Measure it — don't eyeball it

      Stand up a held-out set of realistic, multi-tool tasks ("find every org where experiment X beat its holdout," "at $50k/week and iROAS 3.0, minimum holdout for 80% power") and track, per task: first-try call success, malformed-argument rate, tool-call count, total tokens, and end-to-end accuracy. Run it before and after each phase. The mechanisms in this review predict direction (enums cut malformed args; deferral cuts tokens and lifts selection; canonical names cut chain breaks) — the eval tells you the magnitude on your real workload, and catches any regression a refactor introduces.

      A closing note

      This server is closer to good than the length of this review suggests. It already does the hard, rare things — server-side payload truncation, posterior-probability guidance, scoped permissions, discovery bootstrapping. Its weaknesses are the quiet, compounding kind: one concept wearing four names, a constraint written where the schema can't enforce it, a tool count that blurs selection. Read every fix against the single yardstick from Chapter 1 — can a non-deterministic reader find it, call it right the first time, use what comes back, and chain it onward?

      The good news is the shape of the work: almost every recommendation is additive and measurable. Enums, error boundaries, and clamps ship today with no signature change. The canonical vocabulary ships as aliases that never break a running agent. And nothing here is taste — stand up the eval harness, run it before and after each phase, and let the numbers decide.
