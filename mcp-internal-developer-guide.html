Part I

Orientation — what it is, what the words mean

A read-only data gateway wearing an MCP coat. Before the code, the job it does and the precise vocabulary the rest of the system is written in — this repo is unusually disciplined about its terms.

§00What this service is & why it exists

haus-mcp-internal is an internal MCP (Model Context Protocol) server. It exposes Haus analytics — experiment results, ad-platform metrics, first-party KPIs, attribution, and cMMM model output — as read-only tools that Haus employees invoke from Claude Desktop / Claude.ai / Claude Code. An employee asks Claude a question in natural language; Claude calls the right tool here; the tool queries a backend and returns a structured, agent-friendly answer.

It is built on FastMCP (which sits on Starlette/ASGI), speaks MCP over Streamable HTTP, and is gated by OAuth 2.1 + Firebase. Authorization is delegated to haus-rbac-api — this service never decides permissions itself; it asks. Every tool is readOnlyHint=True.

The whole service is a thin, heavily-guarded translation layer: natural-language question → authenticated, authorized, org-scoped, read-only query → structured answer with provenance. Almost all of its complexity is in the guards (auth, RBAC, cross-tenant isolation, caching) rather than the queries.

Two MCP servers — don't confuse them

The mcp_internal_ permission namespace is permanent precisely because there's a sibling: the external haus-mcp (customer-facing). This repo is the employee server. Same protocol, different audience, different permission namespace.

Pre-refactor state

CONTEXT.md is explicit that the capability taxonomy and tool surface are scheduled for significant reshaping. Several "domains" don't yet line up across permission constants, FastMCP tags, and the tool-reference resource. Treat the five-domain model (Experiments, Metrics, Attribution, cMMM, Organization) as a transitional convention, not ground truth. This is the seed of §16.

Architecture — how the pieces connect

§03The middleware stack (order is load-bearing)

FastMCP middleware is registered outermost-first. The order is not arbitrary — a recent fix (INFR-1254) reordered it, and app.py carries a "DO NOT swap" comment. Here is the stack, request flowing top to bottom:

request ─▶ 1. AuditMiddleware logs EVERY request (even rate-limited ones) → tool_call_completed ─▶ 2. ProvenanceMiddleware injects freshness_sla into analytical responses (no-op for discovery) ─▶ 3. RateLimitingMiddleware per-Caller-Identity budget (UID > email > session); rotation ≠ reset ─▶ 4. CachingMiddleware per-caller key = sha256(identity + tool + json_args); errors never cached ─▶ 5. RetryMiddleware transient retries — ONLY reached on a cache miss ─▶ tool execution ▲ ▲ (responses bubble back up through the same layers) │ └─ Cache MUST be OUTER to Retry: a cache hit short-circuits retry + tool entirely. └──── Audit MUST be OUTERMOST: a rate-limited call is still recorded.

Two ordering invariants, both born from incidents: (1) Audit is outermost so denied/throttled calls still produce an audit row — observability can't be starved by the rate limiter. (2) Caching is outer to Retry so a cached hit never burns retry attempts. Swapping 4 and 5 would re-run the tool on every cached request and defeat the cache. Don't reorder without re-reading INFR-1254.

Three of these are built lazily (build_rate_limit_middleware(), build_caching_middleware(), build_retry_middleware()) because they need the Redis client and settings resolved at startup. AuditMiddleware also emits the RudderStack mcp_tool_called analytics event (a no-op when the write key is unset).

§04Request flow, end to end

A single tool call traverses auth, org resolution, RBAC, execution, and audit. The spine is require_auth() in tools/common.py:

Claude Desktop ──(Streamable HTTP, OAuth 2.1 token)──▶ FastMCP server │ 1. JWT auth HausDomainJWTVerifier: verify Firebase signature, email_verified IS True, │ domain ∈ allowed_domains, reject null-byte tokens. (app.py) 2. org resolve require_auth → _get_org_or_error: │ identity = uid|email (NEVER session_id — F3/F21) │ org_map = Redis cache hit? ── miss ──▶ RBAC GET /orgs/me?permission=experiments:read │ resolve org_name_as_key → org_id (typo-normalize, then ctx.elicit fallback) │ canonicalize: replace('-','_') (F12 — block org-a/org_a dataset collision) 3. RBAC check _check_permission → assert_tool_permission → RBAC POST /permissions/check │ denied → AuthResult.error with {"_outcome":"rbac_denied"}; resolved_org stays NULL 4. set_resolved_org(canonical_key) ← only now, on success 5. tool runs query AlloyDB / BigQuery / Harbor; shape response (+ data_as_of) 6. audit tool_call_completed {tool, requested_org, resolved_org, employee, duration, outcome}

Note the two org fields threaded through context.py contextvars: requested_org is stamped by AuditMiddleware before any validation (so it survives every failure path); resolved_org is set by require_auth only after RBAC grants access. That split (INFR-1234) replaced a single current_org var that was overwritten on every request — it's what makes "find every denied attempt" a clean resolved_org IS NULL query.

§07Two clever bits: sessions & monkey-patches

Redis-backed MCP sessions

The MCP SDK keeps the Mcp-Session-Id → transport map in process memory. With more than one replica (or any restart), a request can land on a pod that doesn't know its session → 404 Session not found → the client reports "server-side session terminated." The fix is RedisStreamableHTTPSessionManager: on initialize it caches the raw request bytes + the notifications/initialized payload in Redis (mcp_session:{id}, 24h TTL). When a request hits a pod that's never seen the session but Redis has it, the pod spins up a fresh transport and replays the cached payloads to reach the same protocol state, then dispatches. Two pods re-hydrating the same session race harmlessly because tool calls are idempotent and each pod owns its own transport.

Why FastMCP gets monkey-patched (ADR-0004)

FastMCP exposes no hook for either of these, so app.py swaps two imported class names before mcp.http_app() builds the ASGI app:

# app.py — both must run before mcp.http_app()
fastmcp.server.http.StreamableHTTPSessionManager = RedisStreamableHTTPSessionManager  # Redis sessions
fastmcp.server.http.RequireAuthMiddleware       = HausRequireAuthMiddleware           # 401s with context

The second swap exists so a bare 401 becomes a structured auth_middleware_401 log carrying firebase_uid_unverified, client_ip, and request_id — making 401 spikes triageable without a code change. Both patches are import-time and order-sensitive; they're the most upgrade-fragile thing in the repo (a theme we return to in §16).

The #1 cause of red CI on correct PRs

Always run make lint before opening a PR, even if the per-commit hook ran. The hook only sees staged files; --all-files catches cross-file drift (e.g. trailing-newline regressions in untouched files). Skipping it is the most common avoidable CI failure here.

Quality gates worth knowing

  • 90% coverage floor (--cov-fail-under=90), ~69 test files, pytest-asyncio in auto mode.
  • A custom pre-commit linter, scripts/check_asyncmock_spec.py, enforces AsyncMock(spec=...) / autospec=True in tests — preventing mocks that silently accept any method.

Part IV

Knowledge base — the load-bearing concepts

The parts that, misunderstood, become security or correctness bugs rather than test failures. Almost every one traces to a numbered security-scan finding (F-numbers) or an ADR.

§10Deep dive: OAuth 2.1, Firebase & DCR

Claude Desktop handles OAuth 2.1 + PKCE natively. This server provides the endpoints and exchanges a Google Sign-In for a Firebase ID token. The auth gate is HausDomainJWTVerifier (subclassing FastMCP's JWT verifier):

# app.py — every layer must pass or the token is rejected (returns None)
if "\x00" in token: return None                  # null-byte tokens
access = await super().verify_token(token)        # Firebase signature + issuer + audience
if claims.get("email_verified") is not True:    # STRICT — truthy "false"/"0" do NOT pass
    return None
if domain not in settings.allowed_domains:      # @hausanalytics.com / @haus.io only
    return None

The is not True check is deliberate: Firebase custom claims can be any JSON type, so a string "false" must never count as verification.

OAuth endpoints & the consent CSRF cookie (ADR-0003)

GET /oauth/authorize renders a consent page and sets an HMAC-signed, HttpOnly _haus_consent cookie binding the in-flight state to this browser; POST /oauth/authorize verifies the cookie before redirecting to Google. This blocks code-phishing on the loopback redirect that Claude Desktop uses. (The HMAC secret is domain-separated from the org-map use via a "consent:" prefix — F10.)

Dynamic Client Registration abuse mitigations (ADR-0002)

/oauth/register issues a fresh client_id (UUID4) per request — no persistence, no secret. Because that's trivially spammable, two Redis-backed guards run before issuance:

GuardMechanism
DCR Slot CapGlobal 100 concurrent clients (dcr:count). Atomic increment; 503 at cap. 24h TTL per client; counter reconciled from live keys on boot to avoid TTL-drift pinning. Global, not per-user.
DCR Rate LimitPer-IP 5 registrations/min (dcr:rate:{ip}, atomic INCR+EXPIRE); 429 on excess. IP from request.client.host, not a raw header. Pre-auth, IP-based.
Token revocation is a known gap (ADR-0006)

/oauth/revoke is a no-op stub returning 200 (to not break RFC 7009 clients) and is deliberately not advertised in the OAuth discovery document. Real sign-out — Firebase revokeRefreshTokens + an auth_time check — is not implemented yet. This is a top candidate in §16.

§11Deep dive: identity-keyed caching & the traps

Caching here is per-human, never per-session — the single most important caching rule in the repo (ADR-0001, and security findings F3/F21).

The cache key is the verified identity (uid → email), never the transport session_id.

_authenticated_identity() resolves uid:<firebase-uid> → email:<email> → None. A None identity means do not cache. This matters because two users can share a session_id through the Redis session-rehydration path; keying on the verified JWT claim keeps them in separate cache slots. The org-map cache (org_map:{sha256(identity)}) and the response cache (sha256(identity + tool + json_args)) both follow this rule.

The Argless Tool Cache Trap

A read-only tool that returns per-caller data but takes no caller-discriminating args (e.g. list_organizations) MUST NOT be cached on {tool, args} alone — it would cross-leak one employee's orgs to another. Either include verified identity in the key or exclude it from _CACHED_TOOLS.

Other cache invariants

Error responses are never cached (F1) — a transient failure must not be served as a sticky answer. Caching is outer to Retry so a hit short-circuits retries. Org-map entries are HMAC-signed outside dev; an unsigned/missing-secret state degrades to a fail-secure no-op rather than serving unverified data.

§12Deep dive: RBAC & the gateway permission

This server delegates all authorization to haus-rbac-api over HTTP (rbac.py). Two calls:

CallUsed for
POST /permissions/checkPer-tool gate. Body {token, org, permission, adapter:"firebase"}. {allowed:true} → proceed; 400/401/403 → PermissionDenied.
GET /orgs/me?permission=Populates the org-map: the orgs where the caller holds the gateway permission.

The gateway permission is mcp_internal_experiments:read. The org-map is built from /orgs/me?permission=experiments:read, so an org only becomes visible (and thus addressable by any tool) if the caller holds experiments-read there. Tool-specific permissions (mcp_internal_kpis:read, ..._attribution:read, etc.) layer on top. The classic confusing denial: a user with kpis:read but not experiments:read on an org won't see that org at all, and a KPI query against it fails as if unauthorized. (See the CONTEXT.md example dialogue.)

Fail-secure on misconfiguration (F7)

assert_tool_permission treats a None RBAC client as a denial outside development. An earlier version returned "allowed" when the client was None — a misconfigured deploy with an empty rbac_service_url silently authorized every employee. Now there's a boot-time audit signal (SECURITY_CRITICAL_MISSING_SECRETS) and this use-site denial as defense in depth. Denials are also worded to deter LLM retry loops (ENA-109): "Do not retry — this denial will not change within this session."

§13Deep dive: cross-tenant safety (IDOR)

The scariest bug class in a multi-tenant data gateway is reading the wrong org's data. Three defenses, each from a numbered finding:

FindingDefense
F12Hyphen normalization at one chokepoint. RBAC may return org-a or org_a; _get_org_or_error canonicalizes '-'→'_' the moment an RBAC-validated key enters the session. Downstream resolve_dataset can then assume the canonical form — otherwise two distinct RBAC orgs could map to one BigQuery dataset.
F2assert_customer_matches_org. BigQuery-attribution tools take both org_name_as_key (RBAC-gated) and a customer arg (used to build the dataset). Since RBAC only adjudicates the former, a caller authorized for org A passing customer=org_b could read B's data. The guard rejects any mismatch; the authorization decision and the data sink must use the same identity.
F17Structured outcome buckets. Audit denials are bucketed on a structured _outcome:"rbac_denied" field, not by substring-matching a free-form message a caller could forge by crafting org_name_as_key.
The unifying principle

Every place where an org identity is used to fetch data must be the same identity RBAC authorized — normalized identically, compared explicitly, and never derived from a second, ungated argument. When you add a tool that takes any org-ish parameter beyond org_name_as_key, you owe it an assert_customer_matches_org-style check.

§14Provenance, taxonomies & the calc mirror

Freshness envelope (ADR-0008)

ProvenanceMiddleware injects a freshness_sla block (max_age_days, breached, source) into every analytical response that carries data_as_of, and is a no-op for discovery tools. Per-source SLA defaults: experiments 3 days, BigQuery attribution 3 days, Harbor cMMM 7 days. This lets the LLM warn a user when it's reasoning over stale data.

Contract-grade taxonomies (ADR-0007)

Outcome strings and Reason Hint strings are a contract with LLM clients and downstream log queries. Additions are non-breaking; renames or removals require a two-release deprecation window emitting both old and new values. The harbor-status classifier in tools/common.py (_classify_harbor_status) is where most reason hints are minted — e.g. a cmmm-serving 5xx carrying "goes beyond model data range" is re-classified as the permanent request_out_of_model_range so the LLM clips its date range instead of retrying forever.

The calculation mirror (ADR-0005)

calculations/cpi.py, nationalization.py, and decomposition.py are 1:1 hand-ports of math in the separate api service, kept independent so the two services deploy without a shared dependency. Each module's docstring names its canonical api source path, and deliberate deviations are called out (e.g. is_holdout_experiment defaults unknown structures to "no scaling," safer for a read-only consumer). The accepted risk: when api's math changes, these drift until manually updated. The 90% coverage gate + dedicated test_calculations_* tests are the current mitigation. This is also a §16 candidate.

§15Debugging decision tree & common issues

"A tool returned an error / denial — why?"

Pull the audit row (jsonPayload.message="tool_call_completed"); read `outcome`: │ ├─ rbac_denied → resolved_org is NULL. §16Potential improvements — and how

The codebase is in genuinely good shape — strong test coverage, an explicit security-finding trail, careful fail-secure defaults, and clear ADRs. The items below are opportunities, several already acknowledged in the repo's own docs. Each carries a confidence level (per Haus epistemic standards) and a concrete approach. None should be read as "this is broken."

1  Reconcile the capability-domain taxonomy high confidence

Observation (verified in CONTEXT.md "Flagged ambiguities"): three taxonomies disagree — permission constants split into ~8 domains, FastMCP tags into 5+, and the _TOOL_REFERENCE resource into 6 categories. Agents (and humans) re-derive the mapping from scratch.

Today

Domain identity is implied by three separate, drifting sources. A new tool can land in inconsistent buckets.

How to improve

Define one canonical enum of capability domains; derive permission constant, FastMCP tag, and tool-reference category from it (single source of truth). Add a test asserting every @mcp.tool maps to exactly one domain across all three. This is owned by the planned refactor — the enum + conformance test is the cheap first step.

2  Implement real token revocation high confidence

Observation (ADR-0006, CONTEXT.md): /oauth/revoke is a no-op stub; real sign-out doesn't exist. A compromised or stale token is valid until Firebase's natural expiry.

How: the ADR already sketches it — add the Firebase Admin SDK, call revokeRefreshTokens(uid) on revoke, and enforce auth_time < tokens_valid_after_time inside HausDomainJWTVerifier.verify_token. Then advertise /oauth/revoke in the discovery document. The verifier is already the right chokepoint; the change is additive and testable against the existing auth tests.

3  Close the calculation-mirror drift risk medium confidence

Observation (ADR-0005): calculations/* are hand-synced ports of api math; drift is an accepted current-state risk mitigated only by coverage.

How (ranked by effort): (a) cheapest — a scheduled "drift detector" CI job that hashes the canonical api source functions and fails when they change without a corresponding change here (turns silent drift into a loud signal); (b) medium — extract the shared math into a small private package both services depend on; (c) heaviest — fetch derived values from Harbor at runtime (removes the duplication but adds a network dependency on the hot path). The strategic call (mirror vs. Harbor-as-upstream) is explicitly an open question owned by Jose; option (a) is valuable regardless of which way that lands.

4  Harden the FastMCP monkey-patches against upgrades medium confidence

Observation (ADR-0004, app.py): two import-time patches replace internal FastMCP symbols (StreamableHTTPSessionManager, RequireAuthMiddleware). They're correct today but silently break if FastMCP renames or relocates those names.

How: add a startup assertion that the target symbols exist and are the expected base classes (fail loud at boot, not mid-request); pin FastMCP to a tested minor range; and add an integration test that boots the app and asserts both the Redis session manager and the enriched 401 path are actually wired. Longer term, upstream a session-manager / auth-middleware hook to FastMCP so the patches can retire.

5  Decouple the gateway permission from a tool domain medium confidence

Observation (tools/common.py): org visibility is built from /orgs/me?permission=mcp_internal_experiments:read. So "can I see this org at all" is welded to "can I read experiments." It's the documented source of the most common confusing denial (§12).

How: introduce a dedicated, domain-neutral gateway permission (e.g. mcp_internal:access) seeded in haus-rbac-api and granted alongside any tool permission, then key the org-map fetch on it. This separates "MCP access" from "experiments access" and makes partial-permission users behave intuitively. Cross-repo (needs an rbac migration), so it's a coordinated change, not a local one.

6  Tame the tool-surface size for the LLM lower confidence

Observation: ~90 tools (metrics.py alone ~36) is a large surface for a model to select from; it inflates the tool-list context and can degrade tool-choice accuracy. (This is an inference about LLM ergonomics, not a measured regression — hence lower confidence.)

How: consider consolidating the many near-identical ad-platform getters behind fewer parameterized tools (e.g. one get_google_ads_performance(level=…, dimension=…) instead of a dozen), and lean on Resources + Prompts for discovery so the hot tool list stays small. Worth measuring tool-selection accuracy before and after; ties into the planned refactor.

7  Finish removing transitional dead code lower confidence

Observation (CONTEXT.md): a legacy session-keyed OrgSession notion is noted as "dead code retained transitionally," and the domain doc flags an unfinished experiment-data-model grilling (structure/type taxonomies incomplete).

How: once the identity-keyed cache is the only path in production, delete the legacy session-keyed remnants and tighten the experiment-model types (add the holdout/no holdout variants the doc says are missing). Low risk, reduces the "two ways to do it" confusion for new readers. Pair it with the scheduled grilling session the doc already names as the owner.

Net read: the highest-value, lowest-regret moves are #2 (token revocation) and #1 (taxonomy single-source-of-truth) — both are already endorsed by the repo's own ADRs/CONTEXT and are largely local. #3a (drift detector) and #4 (patch guard) are cheap insurance. #5 and #6 are bigger, coordinated bets best folded into the planned refactor rather than done piecemeal.

Calibration note: items 1–4 are grounded directly in the repo's own docs/code and are high/medium confidence. Items 5–7 are sound engineering directions but involve judgment calls (cross-repo coordination, LLM ergonomics, refactor sequencing) that the owning team should weigh against roadmap priorities — I have not validated them against runtime metrics or the refactor's current plan.
