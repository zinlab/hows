Part I

Orientation — what it is, what the words mean

Before the code: the job this service does, and the small vocabulary that the rest of the system — and every ADR — is written in. Skip this and the code will read like noise.

§00What this service is & why it exists

haus-rbac-api is the central authorization service for Haus. Its one job is to answer, for every other service that needs to gate behaviour: "Can user X perform action A in org O?" It owns role and permission data, resolves user identity from auth tokens, and exposes a small HTTP surface that other backends call synchronously.

It is authorization, not authentication. Identity (who you are) comes from Firebase; this service decides what an already-authenticated principal is allowed to do. The model is classic RBAC: permissions are bundled into roles, and roles are granted to users through role bindings, optionally scoped to a single org.

The whole system reduces to one sentence: a user's capabilities are the union of the permissions reachable from their role bindings, filtered by org membership. Everything else — the two databases, the jobs, the invariants — exists to make that sentence true, safe, and fast.

Name collision warning

Two unrelated things share the rbac prefix. haus-rbac-api (this repo) is application-layer RBAC — users, roles, permissions, bindings. alloydb-rbac (in gitops_terraform) manages database-engine GRANTs on an AlloyDB instance. They share a word and nothing else. Don't conflate them in conversation or code search.

What's deliberately not here

  • No groups / teams. Bindings are per-user by design. A group abstraction would multiply the surface for privilege-escalation bugs and would need its own ADR.
  • No org/user creation. Org-and-user lifecycle (signup, invites) lives in Harbor + the frontend today. This service is a read-side consumer of those writes (for now — see ADR-0002, "transitional").
  • No authentication. Token issuance and verification are Firebase's job; this service only consumes tokens.

§01The domain vocabulary you must know

These terms are part of the contract (defined in CONTEXT.md). They recur in every route, ADR, and migration. Learn them once here.

TermMeaning
PermissionA capability string in entity:action format (e.g. reports:read, roles:create), max 128 chars. Carries an audience (here called permission_type): internal or external.
RoleA named bundle of permissions. Carries a role_type (internal / external). By invariant, every permission inside a role shares the role's audience. May be immutable.
BindingThe grant of a role to a user, a row (user_id, org_id, role_id). org_id = '' means global (all orgs); a real id means org-scoped.
AudienceWho a role/permission targets. internal = Haus staff only; external = customer-facing. Load-bearing — see §10.
ScopeThe reach of a binding: global or org-scoped.
StaffA Haus employee (identified today via an @hausanalytics.com email on the Firebase record). Always holds at least one global internal binding when active; may also hold org-scoped external bindings (dogfooding / customer-hat).
CustomerA non-Haus user with access to one or more orgs. Never holds a global binding.
MSMMarketing Success Manager — the staff member who owns a customer relationship. Gets an org-scoped Admin and Architect User binding per owned org via the backfill job. The canonical "staff with customer hat."
name_as_keyThe org slug used as the org field in /permissions/check (not the display name). E.g. hausdemo.
Two "Admin" roles — keep them distinct

RBAC Admin is internal, immutable, held globally — for Haus staff to administer the RBAC system itself (roles:*, role_bindings:*, permissions:*). Admin is external, immutable, held org-scoped — "full access to a customer org's product views and settings," granted to MSMs and customer admins. Same word, opposite audience and scope. Never collapse the language.

The mid-migration access model (read this twice)

The platform is moving from "membership = capability" to "binding = capability." The two coexist:

Legacy (Harbor today)

A user_organization row alone confers full access to that org's data. Role bindings are not consulted by most legacy callers.

RBAC (this repo's target)

Membership is necessary but not sufficient. The caller must also hold a binding granting the requested permission.

The migration is per-consumer: each service flips from a legacy membership check to a POST /permissions/check call on its own schedule. Until every consumer flips, all Haus staff retain full access to every customer org (they're auto-added as members at org creation). Closing that exposure is exactly why customer-facing RBAC exists.

§03The three runtime components

One Docker image, three entrypoints, three separately-deployed pods. The split keeps the hot path fast: a slow background job can never degrade /permissions/check.

┌──────────────────────────────┐ client services ───▶ │ haus-rbac-api (web) │ python: uvicorn haus_rbac.main:app (Harbor, MCP, …) │ FastAPI behind GKE Gateway │ ↳ MySQL + PG via ContextVar │ /permissions/check /roles … │ ↳ Redis (rate-limit counters) └──────────────┬───────────────┘ ↳ DevCycle (optional) │ enqueue / consume ┌──────────────▼───────────────┐ cron (UTC) ───────────▶│ haus-rbac-api-scheduler │ python -m haus_rbac.scheduler :00 backfill │ APScheduler BlockingScheduler│ (enqueues RQ jobs only) 02:00 fb replication └──────────────┬───────────────┘ │ Redis queue ┌──────────────▼───────────────┐ │ haus-rbac-api-*-worker │ python -m haus_rbac.worker │ RQ worker + reconnect superv. │ ↳ own DB conns via ContextWorker └───────────────────────────────┘
PodEntrypoint & role
webhaus_rbac.main:app. Serves the public API. Opens MySQL + PG via Cloud SQL Connector at startup (lifespan), threads them through each request via a ContextVar. Also opens a Redis client (rate-limit counters) and an optional DevCycle client.
workerpython -m haus_rbac.worker. An RQ worker on a Redis queue, consuming jobs from haus_rbac/jobs/. Wrapped in an in-process reconnect supervisor so idle Memorystore TLS reaping no longer causes CrashLoopBackOff (it reconnects instead of exiting).
schedulerpython -m haus_rbac.scheduler. An APScheduler BlockingScheduler that only enqueues RQ jobs on a cron schedule (haus_rbac/schedules/). The worker does the actual work.
Why scheduler and worker are separate

The scheduler decides when; the worker does the work. Separating them means a long-running job occupies a worker without blocking the next cron tick, and the web pod stays stateless and fast. Don't move job bodies into the scheduler.

§04The two-database split

RBAC spans two databases on purpose (ADR-0002). Knowing which table lives where is the single most useful fact for debugging a permission check.

MySQL — shared, read-only here

Owned by Harbor (the legacy monolith). Tables: organizations, user_organization, users.

This service's MySQL user holds SELECT grants only. A write here is an invariant violation, not just bad style. It is the authoritative source for "is this org active?" and "is this user a member?"

PostgreSQL — RBAC-owned

Fully owned by this service. Tables: roles, permissions, role_permissions (join), role_bindings.

Schema in haus_rbac/db/schema_pg.sql; evolved with dbmate migrations in haus_rbac/db/migrations/, applied automatically on startup.

The PostgreSQL schema (RBAC core)

CREATE TABLE permissions (
    id            integer PRIMARY KEY,
    name          varchar(128) UNIQUE NOT NULL,   -- entity:action
    description   text NOT NULL,
    permission_type varchar(32) DEFAULT 'internal'  -- internal | external
);
CREATE TABLE roles (
    id          integer PRIMARY KEY,
    name        varchar(128) UNIQUE NOT NULL,
    immutable   boolean DEFAULT false,
    role_type   varchar(32) DEFAULT 'internal'      -- internal | external
);
CREATE TABLE role_permissions (         -- many-to-many join
    role_id int, permission_id int,
    PRIMARY KEY (role_id, permission_id)  -- both FKs ON DELETE CASCADE
);
CREATE TABLE role_bindings (             -- the grant
    user_id varchar(36),                  -- Firebase UID
    org_id  varchar(64) DEFAULT '',         -- '' = GLOBAL (all orgs)
    role_id int REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, org_id, role_id)  -- composite key
);

Note the absence of a standalone index on role_bindings(user_id) — the composite PK's prefix scan covers it for now. See §15 if hot-path latency ever widens.

The org_id = '' convention is everywhere. Empty string means "global, applies to every org." The API boundary translates JSON null ↔ ''; the model layer always stores and compares ''. A NULL in role_bindings.org_id would be a bug.

The fail-closed seam between the two DBs

The two stores can disagree — e.g. a user is removed from MySQL user_organization while a Postgres role_binding still exists. The permission check resolves this by failing closed at the MySQL membership step: no membership ⇒ denied, regardless of the dangling binding. Stale Postgres rows are not actively reconciled today. Deactivating an org (is_active=false) rejects new checks but leaves bindings intact, so reactivation restores prior access — intentional, but an operator footgun if a customer is offboarded for cause and later reinstated.

Knowledge base — the load-bearing concepts

The chapters that pay off most. These are the things that, misunderstood, produce security regressions rather than test failures.

§08Deep dive: the permission-check hot path

POST /permissions/check is the busiest, most security-sensitive route. It is publicly reachable on the internet at rbac.haus.io with no route-level auth — the caller's identity is the token in the request body. Here is the exact sequence (services/permission.py + permission_routes.py):

POST /permissions/check { token, org, permission, adapter? } │ ├─0 4 MB body cap (RequestLoggingMiddleware) ............ 413 if exceeded ├─1 resolve user from token via user_sources adapter ... 200 {allowed:false} if bad ├─2 per-subject rate limit (Redis permcheck::) 200 {allowed:false} if >60/min │ └─ Redis down? FAIL OPEN — request proceeds ├─3 org active? (MySQL: by org_id or name_as_key) ...... 200 {allowed:false} if inactive/missing ├─4 org membership? (MySQL user_organization) ......... 200 {allowed:false} if not a member ├─5 permission held? (PG: binding→role→role_perm→perm) walk global + this-org bindings └─6 RESPONSE 200 {"allowed": true | false} ← all normal outcomes, incl. every deny 422 malformed permission string ← before any DB/Redis work 503 {"detail":" unavailable"}← Firebase / MySQL / PG unreachable

The Postgres permission resolution is a single join (RoleBinding.get_allowed_permissions), including both global (org_id='') and the specific org's bindings:

def get_allowed_permissions(cls, user_id, org_id) -> set[str]:
    query = (
        Permission.select(Permission.name)
        .join(RolePermission)
        .join(cls, on=(cls.role_id == RolePermission.role_id))
        .where((cls.user_id == user_id)
               & ((cls.org_id == "") | (cls.org_id == org_id)))  # global OR this org
    )
    return {p.name for p in query}

Three status codes, three meanings. 200 {allowed:false} = "asked and answered, no." 422 = "your request was malformed." 503 = "I couldn't reach a dependency — retry." Every deny path returns the same 200 body so an attacker can't distinguish "wrong token" from "no permission" from "rate-limited" (status-code parity, ADR-0003 §2). The 503 exists precisely so callers can tell denied apart from unavailable (ADR-0007).

Other routes reuse the same engine

Non-/permissions/check routes don't open-code auth. They depend on one of two FastAPI dependency factories from api/dependencies.py (split by ADR-0008):

DependencyUse when
require_permission("e:a")The route needs a specific permission. Resolves the user, runs check_permission inline, raises 403 on denial. Passing "" raises ValueError at startup — a guardrail.
require_authenticated_user()The route needs a valid token but no specific permission (e.g. /permissions/current_user, /orgs/me).

require_permission has knobs: any_scope (admit any holder regardless of org context), global_only (force org to None), alternatives (pass if the user has the primary or any alternative permission), and body_type (resolve org_id from the request body too). A subtle rule: org-prefixed (org_*) alternatives are never satisfied at global scope, so a per-org permission can't be silently admitted globally.

§09Deep dive: identity & the two Firebases

The adapter pattern

Token → user-record resolution lives in user_sources/, a pluggable registry keyed by adapter name (default "firebase"). Adapters implement the UserSource protocol (find_by_token, find_by_ids, find_by_email[_domain], provision_user) and return plain dicts. The User model is not a Peewee model — it's a plain Python object built from the adapter's dict; it has no table and no DB. 

# How a route ends up with a User — no DB row involved
auth = get_user_from_token(token, adapter)   # → TokenAuthResult
# adapter.find_by_token() returns None (invalid) OR raises:
#   DisabledAccountError  → account disabled in Firebase
#   RevokedTokenError     → auth_time missing or predates revocation cutoff
# the dependency layer maps these to 401 with distinct audit error= fields

Why there are two Firebase projects

A company-wide migration (owned by another team) is moving from a legacy Firebase project to a new one. This service is a consumer of that migration, not its driver.

ProjectRole
Source (legacy)Used by Harbor; MySQL users keys match source UIDs.
Destination (new)What this service validates tokens against on rbac.haus.io. ADR-0003's JWT issuer pin targets this project.

Replication is UID-preserving: a staff member has the same UID in both projects, so Harbor's (user_id, org_id) rows keep matching destination-issued tokens. Customers are destination-only — source Firebase is never in the customer path (resolved in ADR-0006). Token revocation strategy: the 1-hour Firebase TTL is trusted; no active revocation is performed.

§10Deep dive: the audience–scope invariant

This is the single most load-bearing rule in the system (ADR-0001, amended 2026-05-19). Internalize it.

audience = external ⇒ scope = org
(audience = internal permits either scope)

Equivalently:

  • An external role can only be granted via an org-scoped binding (a customer never gets global power).
  • An internal role may be granted globally (full staff authority) or org-scoped (the 2026-05-19 amendment, for narrow "staff inside one org" authority — e.g. an MCP role bound at one customer org).
  • A customer never holds a global binding; staff may hold any combination.

The derived privilege-escalation rule

A caller may create binding B only if some binding C of theirs satisfies C.audience == B.audience and C.scope ⊇ B.scope (global ⊇ org-scoped; equal scopes OK if orgs match). There is no cross-audience grant authority — an external admin cannot mint internal power.

Enforcement is code-only today

The invariant is enforced indirectly in service-layer validation and route restrictions, not yet as a DB-level CHECK on role_bindings. That's the target state. Treat any code that creates bindings as security-critical — a bug here is a privilege-escalation bug, not a 500.

The audience-split (the inverse, for listing endpoints)

When listing bindings/users for a customer org, Haus-internal-domain users (@hausanalytics.com / @haus.io) are stripped from the response — customers shouldn't see Haus staff bound to their org. The exception list is INTERNAL_MEMBERS_ALLOWED_ORGS = {hausdemo, hausstore}. The opt-in inverse (include_internal_users=true) exists for the internal staff-access tool and is gated server-side on the caller's email domain — a customer admin cannot use it to enumerate staff. This filter axis being "request context" rather than "caller identity" caused a real regression on 2026-05-20; the long-term fix is ADR-0009's bounded contexts (§14).

§11Designing permissions & roles

Adding a permission/role is a migration plus, usually, a require_permission call site. The hard part is the naming and scoping decision.

Naming: entity:action

  • Entity = the resource being protected, never a team name. crosswalk_download:read good; data_science:read bad (that's a team).
  • Action is the operation: read, create, update, delete, write.
  • Must match ^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$, max 128 chars.

General vs subsystem-scoped — the decision tree

Will this permission protect an endpoint in a NEW subsystem? ├─ YES → Will that endpoint resolve data accessed from OTHER subsystems? │ ├─ YES → General entity (e.g. orgs:read) │ └─ NO → Subsystem-scoped (e.g. launch_tracker:read) └─ NO → Is the endpoint already protected by another permission? ├─ YES → Reuse that existing permission └─ NO → Does this data entity also exist in other subsystems? ├─ YES → General entity (e.g. users:read) └─ NO → Subsystem-scoped (e.g. wharf_connections:read)

The trap is over-generalizing: a general permission grants access everywhere it's checked. If your tool needs only a narrow slice of an entity, scope it to your subsystem (mcp_internal_kpis:read) so you don't silently widen access elsewhere.

Reuse, don't duplicate

Need org data? Reference the existing orgs:read, not a new my_tool:orgs_read. A role can mix new and existing permissions.

Don't over-scope either

If data genuinely spans subsystems, one general permission beats duplicating scoped copies everywhere.

Role properties & the immutability rule

Default new roles to role_type='internal', immutable=false. immutable=true is set at create time only (no inverse toggle) and locks the role against update/delete via the API — reserved for system-seeded roles (Admin, RBAC Admin, DataOnboardingWorkflowsExecutor, OrgNamesUpdater). DELETE /roles/{id} refuses with 409 if any binding references the role (ADR-0005) — remove bindings first; the old cascade-to-bindings behaviour was rejected for its mass-revocation risk.

§12Background jobs: backfill & replication

Two cron jobs run via scheduler → RQ → worker. Both are additive-only by default — a deliberate choice after a real incident.

admin_role_backfill — hourly at :00 UTC

  • Pulls GET /orgs from hehm-api (Cloudflare Access fenced) to find each active org's MSM (by haus_owner_email).
  • For every active (org, MSM) pair, ensures both an org-scoped Admin and an org-scoped Architect User binding exist (strict-pair semantics). Idempotent — skips existing, never updates.
  • If either role row is missing from roles, the whole run raises RuntimeError and writes nothing — fails loud rather than partial.
  • Prune phase is disabled by default (BACKFILL_PRUNE_ENABLED=false). It once swept manual Admin grants on a demo org absent from hehm-api's /orgs. Re-enable only after adding binding provenance (e.g. role_bindings.managed_by) so manual grants survive; run first with BACKFILL_DRY_RUN=true.

firebase_user_replication — daily at 02:00 UTC

  • One-way, additive-only replication of Haus-domain users only (source → destination Firebase). UIDs preserved, email collisions skipped, domain filter via FIREBASE_DEST_ALLOWED_EMAIL_DOMAINS.
  • Customers never flow through this job — they enter destination Firebase via signup.
FIREBASE_DEST_PURGE_DESTINATION is a loaded gun

Setting it deletes every destination Firebase user and exits. It's a plain boolean with no typed-confirmation guard, by deliberate choice. The operator runbook must require a DRY_RUN=true invocation first (to log the would-be-deleted count) and a written change ticket before flipping it. Treat it as a manual operator action, never an automated path.

§13The security model

Because /permissions/check is reachable from anywhere (six consumers, including external haus-mcp), every defence lives in the application layer, not at the network edge. That is a load-bearing decision, not a gap.

ControlWhat it does
4 MB body capRequestLoggingMiddleware rejects oversized POST/PUT/PATCH bodies with 413 before any handler — guards memory on the unauthenticated endpoint.
Status-code parityEvery deny returns identical 200 {allowed:false} (ADR-0003 §2) — no side-channel enumeration.
Per-subject rate limit60 checks/min/subject via Redis; fails open if Redis is down.
Oracle collapse: 404 over 403Resource-existence endpoints (e.g. GET /users/{id}) return 404 for both "doesn't exist" and "exists but not visible to you" — you can't probe existence.
Audit log linesMutations emit rbac.binding.created/deleted/refused with identifier fields and role_name so access changes are answerable from logs alone.

Log masking policy (obfuscation.py — single source of truth)

Flow through unmasked (identifiers)

user_id, org_id, role_id, binding_id, org. These are stable references operators need, not PII.

Always masked to *** (PII)

email, token, password, secret, api_key, authorization, phone — plus any JWT-shaped value regardless of key, plus anything nested beyond one level.

If you add a genuinely-PII field, extend _PII_KEYS. Never add an identifier to that list — it would blind operators investigating access changes.

§14Feature flags & the bounded-context future

Per-org role visibility (DevCycle)

GET /roles?org_id=<id> filters its response per-org. A static map ROLE_NAME_TO_FLAG in feature_flags.py pairs role names with DevCycle flag keys (e.g. Architect User → arch-show-architect-in-app). A gated role whose flag is False for that org is dropped; unmapped roles always pass through. The lookup is by role name, not permission prefix, so permission naming can evolve without affecting visibility.

Fail-closed

If DevCycle is unreachable or errors, is_org_flag_enabled returns its False default — gated roles disappear. Un-gated roles are unaffected. Existing bindings keep working regardless; only the listing is filtered. customData exposes orgId and orgNameAsKey for targeting rules.

Where this is heading: ADR-0009 bounded contexts

The same routes serve two audiences (customer admins vs Haus staff) with the audience-split rule living inside handlers as conditionals gated on request context. That shape produced the 2026-05-20 regression. The accepted direction is to split at the route layer — the URL becomes the policy declaration:

ContextShape
Customer RBAC/orgs/{org_id}/... — audience-split always on, gated on org_* permissions.
Staff RBAC/staff/... — audience-split does not apply (these exist to show staff); gated on Haus-internal email domain + permission, enforced at the route boundary.

Models, migrations, and the core services (check_permission, audience validation) stay shared. This eventually removes INTERNAL_MEMBERS_ALLOWED_ORGS and the include_internal_users flag.

§15Debugging decision tree & common issues

"My /permissions/check returned the wrong thing"

What did you get back? │ ├─ 422 → malformed `permission` (must match entity:action) or missing body field. │ Fix the request shape; nothing reached the DB. │ ├─ 503 → a dependency is down (body says which: firebase / mysql / postgres). │ This is NOT a deny. Retry. Check the dependency, not the bindings. │ └─ 200 {"allowed": false} → a genuine deny. Walk the path in order: 1. Token valid? → check logs for auth error= (invalid_token/disabled/revoked) 2. Rate-limited? → >60/min for this subject this minute? (Redis permcheck:*) 3. Org active? → MySQL organizations.is_active for that org_id/name_as_key 4. Member of org? → MySQL user_organization row exists for (user, org)? 5. Permission held? → PG: does a binding→role→permission path grant it for org_id='' (global) OR this org_id? ↳ remember: org-scoped bindings for OTHER orgs are intentionally excluded.
The logs answer most of it

Each check emits a structured permission_check line with outcome, reason (e.g. "org deactivated", "user does not have access to org", "no roles for user in org", "permission denied on org bindings"), plus unmasked user_id/org_id/org. Grep those before touching code.
