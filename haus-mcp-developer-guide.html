Part I

Orientation — what it is, what the words mean

The disciplined sibling of haus-mcp-internal: same protocol, opposite audience, and a far stricter architectural rulebook. Start with the 13 principles — they are the Definition-of-Done for every PR.

§00What this service is & why it exists

haus-mcp is the external, customer-facing MCP server. It exposes a Haus customer's own data — experiments, attribution, marketing-mix outputs — to LLM clients (Claude Desktop, claude.ai, ChatGPT, Codex, any MCP-compatible agent) over OAuth 2.1. It is read-only (a hard V1 invariant; any write surface needs a new ADR), and the primary caller is an LLM agent acting on behalf of an authenticated customer — tools are designed against the agent's reading model.

The mission in one line: a customer reaches their own Haus data, via their own identity, through an LLM agent — and never through a second login surface. Authentication is delegated to Ferry (the existing Haus login UI); authorization is delegated to haus-rbac-api; this service owns the MCP protocol surface, the OAuth token machinery, and the tool contracts in between.

External vs internal — the sibling split

haus-mcp (this repo)

Customer-facing. A customer reaches their own org's data via their own Firebase identity, mediated by Ferry. Read-only, V1 = experiments.

haus-mcp-internal (sibling)

Employee-only ops/analytics (Synapse, Hex, internal tools). Shares no code today. If something is only useful to Haus employees, it does not belong here.

V1 status — read honestly

The architecture is mature and complete (full OAuth surface, identity forwarding, the @haus_tool runtime). The data surface is still early: the only customer-facing Tool shipped today is list_organizations. The experiments/attribution/MMM Tools that are the point of the service are the next build-out (see §15). Don't mistake the polished substrate for a finished product.

§01The 13 principles & the vocabulary

This repo is principle-driven. docs/architecture/principles.md lists 13 architecture principles, each with a one-line statement and a yes/no reviewer check — collectively the Definition-of-Done for every PR. Internalize them; most of the codebase's shape falls out of them.

#Principle
1Organize by capability domain, not tech layer (domains/<name>/, not tools/+serializers/).
2Ports & adapters, no exceptions. Tools depend on port protocols, never concrete clients.
3Deep modules — thin interface (1–3 verbs), fat internals.
4Use-cases, not endpoints. Routers dispatch; use-cases execute the business logic.
5Single-source taxonomy. Tag/category/permission lists are generated from @mcp.tool registrations, never hand-maintained.
6Stable taxonomies & contracts — additive-only; renames need a deprecation window. Version goes in @mcp.tool(version=), never the name.
7Caller identity, never session ID — verified UID/email is the cache + rate-limit + audit key.
8Required config fails at boot, not at first request. No wildcard-if-unset on trust boundaries.
9No partial-stub security endpoints in production — implement it or remove it from discovery + document.
10Contracts enforced at boot — freshness/audit/error-envelope asserted by a boot-time registry, not code review.
11Mirror math is a smell — shared logic gets a shared package / contract test / drift detector, never manual sync.
12CONTEXT.md ships with the code that makes it true (descriptive doc, same PR).
13Tools are task-intent shaped, not API shaped — ≤2-call chains, closed verb set, field names in CONTEXT.md.
Cross-repo note

If you read the haus-mcp-internal guide, you'll recognize these principles as the explicit answers to that repo's flagged ambiguities: #5 fixes taxonomy drift, #9 fixes the no-op /revoke, #11 fixes the calculation mirror, #7/#8/#10 harden caching and config. haus-mcp is the greenfield rebuild with those lessons baked into the rulebook.

Part II

Architecture — ports, adapters, and one ASGI process

A Starlette parent hosting a mounted FastMCP child, organized by domain rather than tech layer. Every outbound call crosses a port boundary; every Tool comes through one decorator that the boot sequence polices.

§02Hexagonal layout: domains, ports, use-cases

The source tree is organized by capability domain (principle #1). Cross-cutting concerns live at package root; everything else lives under exactly one domains/<name>/.

haus-mcp/ ├── src/haus_mcp/ │ ├── app.py ← composition root: build_app() wires every client + the OAuth route table │ ├── server.py ← prod entrypoint (uvicorn against haus_mcp.app:app) │ ├── config.py ← Settings (pydantic-settings); boot-time required-config registry │ ├── context.py ← AppContext (long-lived collaborators) + per-request ContextVars │ ├── logging.py / request_logging.py / obfuscation.py ← structured JSON logs + PII masking │ ├── metrics.py ← OTel counters (safe no-op when no MeterProvider) │ ├── health.py ← /health probe │ ├── tool/ ← CROSS-CUTTING tool runtime (not a domain): │ │ ├── core.py ← Identity, Invocation, @haus_tool, boot-time contract registries │ │ └── response.py ← ToolResponse[T] error-envelope builder │ └── domains/ │ ├── oauth/ ← authz-code + PKCE-S256 + DCR (7591) + mgmt (7592) + introspect (7662) │ │ └── use_cases/ ← authorize, callback, exchange, issue_tokens, register, revoke, introspect… │ ├── identity/ ← FirebaseIdTokenForwarder (mints fresh Firebase ID tokens downstream) │ ├── rbac/ ← RbacPort (the authorization Port) + RbacClient (its only Adapter) │ └── organization/ ← list_organizations — the reference "thin Tool over use-case" ├── docs/ (architecture/{overview,principles}.md, adr/ ×10, adding-a-tool.md, runbooks/) ├── tests/ (unit / wire / Tilt tiers + eval/ tier; ~93% coverage, floor 85%) └── pentest/ (standalone Poetry env; OAuth + auth-enforcement + input-validation probes)
Tools speak only to Ports. The Adapter is wired once in build_app(); the Tool never imports a concrete client.

The flow of dependency is always Tool → Use-case → Port ← Adapter. The reference is list_organizations: a thin Tool that calls list_organizations_impl(rbac_client: RbacPort); the unit tests substitute a FakeRbacPort for the real RbacClient with zero Tool changes (principle #2). New code lands under one domain subtree (principle #1) and exposes 1–3 verbs (principle #3).

§03Runtime composition

A single ASGI process: a Starlette parent app with a FastMCP child mounted at /v1/mcp. All long-lived collaborators are built once in build_app() and shared — no per-request client construction.

ComponentOwns
Starlette parentOAuth routes (/oauth/*), discovery (/.well-known/*), /health, and the mounted FastMCP child.
FastMCP childThe MCP protocol surface at /v1/mcp; tool registration + a lifespan-scoped AppContext.
AppContextThe long-lived collaborators (Redis, Firestore, Firebase, KMS-wrapped Tink keyset, RbacClient, FirebaseIdTokenForwarder) handed to every Tool via Invocation.
BearerAuthMiddlewareGates /v1/mcp* on a valid MCP JWT; returns RFC 9728 WWW-Authenticate + resource_metadata= on 401 so clients self-discover the auth server. Stamps mcp_claims + Sentry user-scope on success.
RequestLoggingMiddlewareStructured request/response logging, body/query obfuscation, request_id ContextVar from the W3C traceparent header (joins logs + audit + OTel trace).

The prod entrypoint is python -m haus_mcp.server, which runs uvicorn against haus_mcp.app:app. Boot is built from a required-config registry (_REQUIRED_IN_NON_DEV): missing secrets fail loud at startup (principle #8), never silently at first request.

§04The two request flows

First-time customer — the OAuth dance

MCP client (Claude Desktop / claude.ai / ChatGPT / Inspector) │ 1. POST /v1/mcp (no token) ▼ BearerAuthMiddleware → 401 + WWW-Authenticate resource_metadata=…/.well-known/oauth-protected-resource (RFC 9728) │ 2. GET /.well-known/oauth-protected-resource (discovery) │ 3. POST /oauth/register (RFC 7591 DCR — per-IP rate-limited) │ 4. GET /oauth/authorize ──302──▶ ferry/login (carries opaque mcp_state) ▼ ferry React login UI: user authenticates with Firebase │ 5. GET /oauth/callback?code=…&firebase_id_token=… (use-case: BridgeOAuthCallback) │ → store encrypted refresh token in Firestore → mint MCP auth code → 302 back to client │ 6. POST /oauth/token grant=authorization_code (use-case: IssueTokenPair) │ → verify PKCE-S256 → mint MCP access token (HS256, 1h) + refresh token (opaque, 30d, single-use) ▼ 7. POST /v1/mcp Authorization: Bearer → tool dispatch

Steady-state tool call

POST /v1/mcp Authorization: Bearer ▼ BearerAuthMiddleware: verify HS256 + iss + aud + exp → scope.state.mcp_claims = AccessTokenClaims(uid,email) ▼ @haus_tool wrapper: build Identity from mcp_claims → build Invocation(identity, app_context) → call Tool ▼ Tool body (e.g. list_organizations): │ RbacPort (RbacClient adapter): │ FirebaseIdTokenForwarder.get_fresh_id_token(uid) ── Redis hit? (50m TTL) ── miss → Firestore refresh-token │ → securetoken refresh → cache │ httpx GET haus-rbac-api Authorization: Bearer (never the MCP token) ▼ serialize → ToolResponse envelope (always HTTP 200) → @haus_tool emits one audit_event log line

The two-token rule: the MCP access token (HS256, ours) authenticates the agent to us; a fresh Firebase ID token (forwarded) authenticates the customer to downstream Haus services. haus-mcp never forwards its own token downstream and is not in any downstream service's trust chain — they all keep authenticating against Firebase.

§06The @haus_tool runtime & boot contracts

@haus_tool (in tool/core.py) is the only Tool registration path (principle #10). It does four things: reshapes the FastMCP-visible signature to drop identity + app_context from the wire schema (they're injected, never client-supplied), builds the async wrapper, records the Tool in three boot registries, and emits one audit_event log line on every call. 

@haus_tool(
    mcp,
    version="1.0",
    freshness=Freshness(max_age_seconds=0, basis="rbac-api GET /orgs/me at call time"),
    audit=Audit(subject_org_field=None),   # None = not org-scoped (list_organizations itself)
)
async def list_organizations(*, identity: Identity, app_context: AppContext) -> dict:
    return await list_organizations_impl(
        firebase_uid=identity.firebase_uid,
        rbac_client=app_context.rbac_client,   # typed as RbacPort, not RbacClient (principle #2)
    )

Every arg/field name (operating_org_id, name_as_key, …) must also appear in CONTEXT.md — asserted at boot (principle #13).

Three boot-time registries (principle #10 — contracts don't decay)

On startup, assert_tool_contracts(mcp) walks the FastMCP tool list and refuses to start unless every registered Tool appears in all three registries: the @haus_tool set (so Identity is reached only through Invocation), a Freshness declaration (staleness posture: max_age_seconds=0 = always hit source-of-truth), and an Audit declaration (so a UID-stamped audit line flows). A Tool registered directly with @mcp.tool — bypassing the trust boundary — crashes the boot. Opt-in contracts decay; boot-time registries don't.

The audit_event line carries tool, tool_version, cleartext firebase_uid (the audit subject — principle #7), outcome (success / the envelope's error code / exception), operating_org_id, duration_ms, and the declared freshness. The outcome is derived from the response envelope automatically — no per-Tool emission code to forget.

Part IV

Knowledge base — the load-bearing concepts

Four deep dives that, misunderstood, become security or correctness bugs. Each is anchored to an ADR and a numbered security finding (H/M-numbers).

§09Deep dive: ferry-mediated OAuth & two tokens (ADR-0001)

The forcing question: how does an agent get credentials to reach a customer's data without haus-mcp becoming a second login surface or leaking Firebase credentials? The answer: mediate through Ferry, issue our own MCP tokens, forward fresh Firebase ID tokens downstream.

MechanismDetail
Ferry owns login/oauth/authorize 302s to ferry_login_url; Ferry posts the customer's Firebase ID token back to /oauth/callback. We never render a login page or see a password.
Full OAuth surfaceAuthz-code + PKCE-S256 required (plain refused), DCR (RFC 7591), DCR management (7592), opt-in introspection (7662), revocation (7009). DCR is per-IP rate-limited (5/60s) so an unauthenticated caller can't mass-write Firestore.
MCP tokensHS256 access token (aud = …/v1/mcp, 1h); opaque refresh token (30d, rotates every refresh, single-use, forms a revocation family). Refresh tokens are resource-pinned (RFC 8707) — a form_resource mismatch raises invalid_target (HIGH 2).
Downstream authFirebaseIdTokenForwarder mints a fresh Firebase ID token from the encrypted refresh token (Redis cache 50m, strictly under Firebase's 60m). Every downstream adapter forwards that, never the MCP token.
Encrypted storageRefresh tokens persist in Firestore, Tink envelope-encrypted. In staging/prod the KEK is KMS-wrapped; boot raises if kms_kek_resource_name is unset (H1) — a process-local key would invalidate all ciphertext on restart.
This is how the internal repo's revocation gap was avoided

Per principle #9, /oauth/revoke here is strict, not a stub: it deletes the refresh-token entry, revokes the whole family, deletes the Firestore doc, and invalidates the cached Firebase ID token in Redis (so downstream tools immediately stop seeing a valid token). A wire test asserts the side effect fires. Introspection (/oauth/introspect) is the inverse: until a consumer needs it, it's removed from discovery entirely rather than shipped as a partial stub.

§10Deep dive: the No-Cache authorization invariant (ADR-0002)

Principle #7 permits caching when keyed by identity. But authorization-derived data (which orgs a customer can access) is a stale-authorization vector at any TTL. ADR-0002 resolves the tension with a single bright line:

Identity caches are allowed. Authorization data is never cached. Ask rbac-api fresh on every relevant call.
Identity cache (allowed)

The Firebase ID token, in Redis keyed by firebase_uid, 50m TTL. It caches who the customer is, and expires under Firebase's own token lifetime.

Authorization data (banned from cache)

Org memberships, permissions. Asked fresh from rbac-api every call. A revoked customer loses access immediately — no TTL window to reason about.

Consequences encoded as rules: rbac-api is the sole source of truth (no local mirror — principle #11); the authorization Port is RbacPort (fetch_user_orgs today, check_permission when the first permission-gated Tool lands); org scoping is per-call, never per-session (every org-scoped Tool takes org_name_as_key and echoes operating_org_id — no server-side "current org"); and at most one authorization check per Tool call (tools needing more are split — principle #3).

The cost, stated plainly

Every org-scoped Tool call costs at least one rbac-api RPC on the hot path (bounded by the 5s timeout). That's the deliberate price of zero stale-authorization risk. It's also why rbac-api retry/backoff (§15) matters — it's a single-shot call on the critical path today.

§11Deep dive: the org resolution protocol (ADR-0005)

Because there's no server-side "current org," the agent must resolve which org to act on. The protocol is deterministic:

Agent needs to make an org-scoped call: 1. call list_organizations first 2. is default_org_name_as_key set? (single-org customer) YES → use it silently NO → ask the user to pick from `organizations` 3. pass the chosen org_name_as_key as an explicit Tool argument 4. the Tool echoes operating_org_id in its response envelope ← audit + agent confirmation

This keeps conversation state in the LLM client where it belongs, gives audit logs an operating_org_id per call, and makes cross-org reasoning bugs visible on the wire rather than hidden in server state. The single-org silent default keeps the common case to a ≤2-call chain (principle #13).

§12Deep dive: Tool design discipline (ADR-0003/0006/0007)

Tools are designed for an LLM reader, and the rules are mechanically enforced so they can't quietly drift.

RuleWhat & where
Intent shape (0006)Answer a domain question in ≤2 chained calls from cold credentials (≤3 with justification). Closed verb set; banned prefixes/suffixes; ≤6 combined params; split into a variant Tool only when one of four conditions breaks. Boot-tested in tests/tool/.
Description contract (0007)Four-part description, ≤600 words. Descriptions are part of the schema — a silent edit changes agent behavior — so a description-snapshot diff runs in CI.
Versioning (0003 / #6)Tool names are stable for life. Versions live in @mcp.tool(version="1.1"); FastMCP routes to the highest and keeps older versions callable for pinned clients. Never get_resource_v2.
Single-source taxonomy (#5)Tag/category/permission indexes are generated from @mcp.tool registrations at boot/build time — never a hand-maintained list (the exact drift that bites the internal repo).
Error envelope: always HTTP 200

The unhappy path is a Pydantic model with error + error_description plus domain fields at their defaults — returned as HTTP 200, with the error in the JSON. Defaults mirror the success shape so the agent parses uniformly without branching on error. Built once per Tool via ToolResponse[T]; FastMCP derives the output schema from the return annotation.

§13Deep dive: the security posture

The OAuth ADR is essentially a catalogue of closed findings (H = high, M = medium, C = CORS). The recurring shape: a trust-boundary decision made explicit, enforced at boot or in middleware, and asserted by a test.

ControlDetail

§15Potential improvements — and how

Unlike a typical "things to fix" list, most of haus-mcp's gaps are tracked next steps the repo names itself — the architecture is deliberately ahead of the feature set. The 13 principles already pre-empt the classic MCP pitfalls (taxonomy drift, no-op revoke, mirror math, session-keyed caches). The opportunities below are mostly about finishing the product on top of a finished substrate. Each carries a confidence level.

1  Ship the actual data Tools high confidence

Observation (CONTEXT.md + source): CONTEXT says "V1 surfaces experiments data," but the only customer-facing Tool that exists today is list_organizations. The substrate (OAuth, identity forwarding, @haus_tool, the org-resolution protocol) is built and waiting; the value-delivering Tools are not.

How: land an experiments domain (then attribution, MMM) per docs/adding-a-tool.md — task-intent-shaped Tools (get_experiment_summary, list_experiments, compare_experiments) over an ExperimentsPort, each with a response model, freshness/audit declarations, and eval scenarios. This is the primary roadmap item, not a cleanup.

2  Implement RbacPort.check_permission high confidence

Observation (ADR-0002): RbacPort is single-method today (fetch_user_orgs). The second verb, check_permission(firebase_uid, org_id, permission), is explicitly deferred "until the first permission-gated Tool lands." Every data Tool from #1 will need it.

How: extend the Port + RbacClient adapter to call rbac-api's POST /permissions/check with the forwarded Firebase ID token, keeping the one-check-per-Tool-call rule (ADR-0002 #7). Lands naturally alongside the first experiments Tool.

3  Add retry/backoff (and a circuit breaker) to the rbac hot path medium confidence

Observation (architecture overview §2): the rbac-api call is httpx.Timeout(5.0) and single-shot; "retry/backoff is a tracked follow-up." Because authorization is never cached (ADR-0002), this RPC is on the critical path of every org-scoped Tool call — a single transient blip becomes a user-visible tool failure.

How: bounded retry with jitter on the idempotent GET, plus a circuit breaker so a sustained rbac outage fails fast rather than tying up the 5s timeout per call. Pair with the Firebase-ID-token cache-hit metric (ADR-0002 names it the one authorization-adjacent signal worth watching) to distinguish auth-mint failures from rbac failures.

4  Finish the observability wiring medium confidence

Observation (overview §2, README): OTel instrumentation runs against no-op providers today; Sentry is DSN-gated; alerts/on-call are "not configured pre-pilot." The wiring is tracked as MCP-177 (deploy-side observability) + MCP-178 (dashboard).

How: complete MCP-177/178 — point the OTel exporter at the collector, set the Sentry DSN per env, and build the dashboard around the audit_event stream (outcome rates, p99 duration, rbac latency) and the OAuth rate-limit / token-mint counters already emitted by metrics.py. The signals exist; they just need sinks.

5  Replace the trivial /health with a real readiness probe medium confidence

Observation (overview §4): /health is a single trivial-200 serving both liveness and readiness; "real dependency-reachability checks are tracked separately." Today readiness can pass while Redis, Firestore, or rbac-api are unreachable — so a degraded pod still receives traffic.

How: add a /ready that checks Redis ping + Firestore reachability + rbac-api liveness (the pattern the internal MCP and rbac-api already use), wired to the k8s readinessProbe while /health stays the liveness probe. Keep it cheap and cache the result briefly to avoid probe-storm load.

6  Scale beyond a single replica medium confidence

Observation (overview §4): staging and prod run a single replica; "multi-replica + HPA + PDB are tracked follow-ups." Single replica means no headroom and a restart is a brief full outage.

How: the design is already horizontally safe — OAuth in-flight state, the ID-token cache, and rate-limit buckets all live in Redis, and there's no server-side session state (principle #7). So the work is mostly chart/infra: bump replicas, add an HPA on CPU/RPS, and a PodDisruptionBudget (minAvailable: 1, matching the rbac-api convention). Verify the rate-limiter's per-IP/per-identity buckets behave correctly across replicas first.

7  Write the runbooks before the pilot lower confidence

Observation (README): docs/runbooks/ is empty; the only operational guide is the OAuth local-testing troubleshooting section. Pre-pilot that's tolerable; at customer-pilot it's a gap.

How: capture recovery steps for the predictable incidents — boot-config failure, rbac-api outage, Firebase refresh failure, Redis unavailability, KMS/KEK rotation — as docs/runbooks/<symptom>.md, referenced from the matching ADR. Cheap, and exactly the kind of thing that's painful to write mid-incident.

Net read: this repo's "improvements" are a roadmap, not a remediation list. #1 (data Tools) + #2 (check_permission) are the product. #3–#6 are the operational hardening that should land before a real customer pilot (and the design already supports them). #7 is cheap insurance. Notably, the things that needed fixing in the internal MCP are here prevented by construction via the 13 principles — so the honest assessment is "finish building," not "fix what's broken."

Calibration note: items 1–2 are verified directly against the source (only list_organizations exists; RbacPort is single-method) — high confidence. Items 3–6 are the repo's own documented tracked follow-ups — medium confidence on the what, with the how being conventional engineering I have not validated against the current infra/chart. Item 7 is an observation about an empty directory. None were validated against runtime behavior or the team's current sprint plan.
